PROBLEM

Clean room objects change silently

External systems (XMI UI, customer integrations) hold references to Questions, Data Connections, Exports. When state changes, those references go stale with no notification.

QUESTION

Output columns removed

A question's dimensions change from 5 columns to 3. XMI's dashboard was built expecting all 5. Breaks silently — no warning sent.

  • Dataset assignments swapped
  • Question renamed or deleted
  • Status DRAFT → PUBLISHED
DATA CONNECTION

Field type changed

purchase_count changes from Integer to String. SQL using SUM(purchase_count) now fails at runtime. Schema consumers have no advance notice.

  • Field added or removed
  • Data connection deleted
  • Any question referencing it breaks
EXPORT / FLOW

Status invisible to integrations

Export job completion, failure, or configuration changes are not pushed to anyone. External systems poll repeatedly to detect state.

  • 99% of polls return "no change"
  • Wasted API calls, compute, network
  • Reactive posture — not enterprise
Two audiences need different solutions: Human users need an audit trail UI. Programmatic systems (XMI, SafeHaven) need push webhooks.

V2 · DELIVERY INTERNALS

Worker Flow — From SQS to XMI Endpoint

Every step is deliberate. Write before ACK. Check before POST. Circuit break on sustained failure.

CALLBACK DELIVERY WORKER — STEP BY STEP
1. receiveMessage(SQS) ← visibility timeout 30s starts
2. CHECK delivery_log ← already delivered? skip
3. query callback_registrations ← find cb-456
4. build JSON payload ← from event
5. HMAC-SHA256(secret, body) ← X-Habu-Signature
6. circuitBreaker.check(url)
CLOSED → proceed   OPEN → fail fast (no HTTP)
7. HTTP POST to callback URL
8. WRITE delivery_log ← BEFORE ACK ← critical order
9. deleteMessage(SQS) ← ACK
FAILURE PATH:
retry 1s → 5s → 30s → max retries → DLQ
DLQ → CloudWatch alarm → PagerDuty
ACK EXPLAINED

ACK = deleteMessage() — explicit, not automatic

Reading from SQS only hides the message for 30s (visibility timeout). It is NOT deleted. You must call deleteMessage() to permanently remove it. If worker crashes before ACK, message reappears and is retried. This is the safety net.

CIRCUIT BREAKER — 3 STATES

Resilience4j — one annotation in Java

CLOSED → normal, calling endpoint on every event

OPEN → 5+ consecutive failures, stop calling for 60s, fail fast, free worker threads

HALF-OPEN → try 1 call after cooldown, if 200 → CLOSED, if 5xx → OPEN again

FAN-OUT

One SNS topic → N independent queues

XMI has SQS-XMI. SafeHaven has SQS-SafeHaven. Each queue is independent — XMI being down does not delay SafeHaven. Adding new consumer = new SQS subscription. Zero code change to unhygienix.

V3 · SPRINTS 6–7

Production Hardening — Enterprise-Grade

No new tables. Extends existing delivery worker and adds a Webhooks UI tab. Makes the system provably correct, observable, and self-serviceable.

SECURITY

HMAC Signature Verification

X-Habu-Signature: sha256=... on every outbound POST. Per-registration secret — XMI's secret is different from SafeHaven's. Timestamp header prevents replay attacks. XMI verifies on receipt — rejects if mismatch.

RESILIENCE

DLQ Admin UI + Replay

New Webhooks tab in clean room UI. Shows delivery status per registration — green/red, last delivered, success rate. DLQ panel lists failed messages with one-click Replay button. Moves message back to main SQS queue.

OBSERVABILITY

Delivery Metrics Dashboard

CloudWatch metrics: delivery success count, failure count, latency histogram, DLQ depth, circuit open count — all by registration and endpoint. Alarm on DLQ depth > 0 → PagerDuty.

TESTING

Webhook Test Endpoint

POST /callbacks/{id}/test — sends a synthetic event to the registered URL immediately. Returns http_status, response_time_ms, success flag. XMI can validate their endpoint is reachable before going live.

REPLAY

Event Replay API

GET /cleanrooms/{id}/events/{eventId}/replay — re-delivers a specific event from the object_events table to all registered callbacks. For missed or failed deliveries. Queries the durable log, not the queue.

IDEMPOTENCY

At-least-once + Dedup

SQS guarantees at-least-once. X-Habu-Event-Id header on every POST lets XMI deduplicate. Worker checks delivery_log before POSTing — if already delivered, skip POST, ACK SQS. Two-layer defence.
