```

            cleanroomId: cr-abc

            objectId: q-123

    No server required on XMI side
    No inbound port to expose
    Org-filtered by JWT claim"

=== BOTTOM STRIP — two boxes side by side ===

Box (green): "Why this approach"
  - Same gRPC endpoint powers both UI and external API — zero duplication
  - Cloud-agnostic: XMI on GCP, MSFT on Azure, both call same REST API
  - Org filtering built-in via JWT — no additional work per new customer
  - Activity Feed UI + downloadable audit logs — additional platform utility
  - Zero XMI infrastructure — no server, no inbound firewall rule needed

Box (yellow): "Trade-offs"
  - Change latency = polling interval (30-60s)
  - XMI must manage cursor state across poll cycles
  - Wasted calls when nothing changed (mitigated with ETag / 304 Not Modified)
  - Platform principle: polling at scale can be rate-limited / throttled

Orange = external API channel. Rounded box corners, drop shadows, directional arrow labels.
Monospace font for API paths, schema fields, and JSON. Enterprise architecture style.
```

## Prompt 2 — Approach 2: Cloud-Agnostic Webhook / Callback Registration (Push)

```
Create a swimlane sequence diagram titled:
"Approach 2 — Webhook Callback Registration (Push)"
Subtitle: "Consumer registers once. Habu pushes events automatically. Works on any cloud."

THREE vertical swimlanes:
  Lane 1 (orange): "XMI UI — Google Cloud"
  Lane 2 (blue):   "Habu Platform (unhygienix + external-api-server)"
  Lane 3 (purple): "Async Delivery Infrastructure (SNS → SQS → Worker)"

=== PHASE 1 — label "One-time Setup" at top ===

Lane 1 → Lane 2, arrow labeled "POST /cleanrooms/{crId}/callbacks":
  Request body box (monospace):
    objectType:      QUESTION
    objectId:        null  ← all questions in this cleanroom
    callbackUrl:     https://xmi.liveramp.com/habu-events
    monitoredFields: [dimensions, status, name, datasetAssignments]
    authConfig:      { authType: BEARER, authValue: eyJhbGci... }

Lane 2 internal:
  Box: "external-api-server validates request"
  Arrow down: "store registration"
  Box: "callback_registrations table (unhygienix DB)
    id: cb-456 | cleanroom_id: cr-abc
    object_type: QUESTION | object_id: NULL (= all questions)
    callback_url: https://xmi.liveramp.com/habu-events
    signing_secret: whsec_a3f9c2... (encrypted at rest)"

Lane 2 → Lane 1, arrow labeled "201 Created":
  Response box:
    id: cb-456
    signingSecret: whsec_a3f9c2...
  Note: "XMI stores signingSecret — used to verify inbound requests are genuinely from Habu"

=== PHASE 2 — label "Runtime: when object changes" in middle ===

Lane 2 internal:
  Box: "sarah@acme.com removes columns from Question q-123"
  Arrow down: "unhygienix CRUD interceptor fires"
  Two parallel arrows labeled:
    Left: "[IN DB TRANSACTION] INSERT object_events — evt-789"
    Right: "[POST COMMIT ~1ms, non-blocking] SNS publish"
  Arrow back up to caller: "200 OK returned immediately — user's operation NOT blocked"

Lane 2 → Lane 3, arrow: "SNS topic: habu-object-events → fans out to SQS-XMI-Delivery"

Lane 3 internal:
  Box: "SQS-XMI-Delivery queue — ISOLATED per consumer"
  Note: "XMI queue failure does NOT affect MI, SafeHaven, or any other consumer"
  Arrow down: "Callback Delivery Worker reads message"
  Box (detailed): "Worker steps:
    1. receiveMessage — visibility timeout 30s (message hidden, not deleted)
    2. Query callback_registrations WHERE cleanroom=cr-abc AND type=QUESTION → cb-456
    3. Build CloudEvents JSON payload from evt-789
    4. HMAC-SHA256(signingSecret, payload) → X-Habu-Signature header
    5. HTTP POST to https://xmi.liveramp.com/habu-events
    6. Write delivery_log: attempt=1, http_status=200, latency=45ms
    7. deleteMessage — explicit ACK"

  Box to the right (failure path, red):
    "On failure: SQS visibility timeout expires → message reappears
     Retry 1: 1s delay
     Retry 2: 5s delay
     Retry 3: 30s delay
     maxReceiveCount=3 exceeded → Dead Letter Queue (SQS-XMI-DLQ)
     CloudWatch alarm → XMI on-call (consumer responsibility)"

Lane 3 → Lane 1, arrow "HTTP POST — CloudEvents envelope":
  Headers box:
    Authorization: Bearer eyJhbGci...
    X-Habu-Signature: sha256=a3f9c2...
    X-Habu-Event-Id: evt-789
    X-Habu-Timestamp: 1715521200
  Body box (CloudEvents format):
    {
      specversion: 1.0
      id: evt-789-uuid
      source: urn:habu:cleanroom:cr-abc
      type: com.habu.cleanroom.question.updated
      time: 2026-05-12T10:32:00Z
      data: {
        orgId: org-xyz
        cleanroomId: cr-abc
        objectType: QUESTION
        objectName: Revenue Analysis
        changeType: UPDATED
        changedFields: {
          dimensions: { removed: [customer_segment, channel] ... }
        }
        changedBy: sarah@acme.com
        schemaVersion: 1
      }
    }

Lane 1 internal:
  Box: "XMI verifies HMAC-SHA256 using stored signingSecret"
  Box: "Dedup: check X-Habu-Event-Id against processed IDs (Redis TTL 7d)"
  Box: "Updates UI — invalidates cache — triggers downstream workflow"
  Arrow back to Lane 3: "Returns 200 OK"

=== BOTTOM STRIP — two boxes side by side ===

Box (green): "Why this approach"
  - True push — XMI reacts in seconds, not 60s polling interval
  - Cloud-agnostic HTTPS: works with XMI on GCP, MSFT on Azure, any future customer
  - Consumer isolation: SQS-XMI failure never affects SQS-MI or SQS-SafeHaven
  - Self-service: teams register via API — no Habu human involvement per new consumer
  - Adding new consumer (MI team) = new SQS subscription only, zero code change in unhygienix

Box (yellow): "Trade-offs"
  - Requires XMI to expose an HTTPS endpoint (inbound from Habu)
  - New infrastructure: callback_registrations + delivery worker + DLQ + CloudWatch
  - More sprints than Approach 1 alone (3-5 sprints on top of V1 Activity Feed)

COLOR: Lane 1 = orange, Lane 2 = blue, Lane 3 = purple, failure path = red.
Timing annotations on key arrows. Monospace font. Enterprise architecture style.
```

## Prompt 3 — Approach 3: Cloud-Native SNS/SQS Internal → Per-Cloud Queue Delivery

```
Create an enterprise architecture diagram titled:
"Approach 3 — Cloud-Native Event Streaming (SNS/SQS → Per-Cloud Queue)"
Subtitle: "Habu publishes internally. External consumers receive on their own cloud queue."

LAYOUT: Top-down main flow, horizontal fan-out in the middle.

=== TOP — Mutation Layer (blue, horizontal row) ===

Three boxes side by side:
  Box 1: "unhygienix — Question mutations"
  Box 2: "unhygienix — Data Connection mutations"
  Box 3: "cronos / picanmix — Export Job mutations"

All three arrows converge DOWN to:

=== INTERCEPTOR LAYER (purple) ===

Box: "CRUD Interceptor — unhygienix"
  [1] Snapshot BEFORE | [2] Execute mutation | [3] Build ObjectEvent + diff

  Two arrows out:
  Left "[IN DB TRANSACTION]" → object_events table → Activity Feed UI (green, same as Approach 1)
  Right "[POST COMMIT ~1ms]" DOWN to:

=== SNS LAYER (orange) ===

Box: "SNS Topic — habu-object-events (picanmix)"

THREE arrows fanning DOWN:

Arrow 1 → Box: "SQS Internal Queue — Habu services only"
Arrow 2 → Box (HIGHLIGHTED orange): "GCP Pub/Sub Subscription
                                       For XMI UI — Google Cloud
                                       habu-cleanroom-events-xmi"
Arrow 3 → Box (yellow): "Azure Service Bus
                          For MSFT (future) — Azure
                          habu-cleanroom-events-msft"

=== XMI GCP DELIVERY PATH (detailed) ===

Below GCP Pub/Sub box → Box (orange): "XMI GCP Project
  Reads from Pub/Sub topic natively
  No HTTPS endpoint required on XMI side
  GCP IAM service account — no Bearer token"

TWO side boxes (RED — complexity warnings):

  Side box LEFT: "Habu must provision per customer:
    GCP: Create Pub/Sub topic, grant XMI service account Subscriber IAM role
    Azure: Create Service Bus namespace, configure RBAC for MSFT
    AWS SNS: Cross-account subscription with customer SQS ARN
    EACH CLOUD: different SDK, different auth model, different error handling
    Egress cost: data leaving AWS → GCP billed per GB per month"

  Side box RIGHT: "Operational risks:
    - XMI rotates service account → Habu loses publish access silently
    - Org isolation: must filter per-topic or per-message attribute (complex)
    - Worker code must branch per cloud (if GCP: use pub/sub SDK, if Azure: Service Bus SDK)
    - Future team MI on different cloud = another SDK to build + maintain
    - Violates vendor-neutral principle"

=== BOTTOM COMPARISON TABLE ===

Wide box — full width:
  Title: "Approach 3 (cloud-native) vs Approach 2 (HTTPS webhook)"
  | | Approach 3 (cloud-native) | Approach 2 (HTTPS webhook) |
  | XMI setup | GCP service account + Pub/Sub | HTTPS endpoint route |
  | MSFT setup | Azure SDK + Service Bus | Same HTTPS pattern |
  | Habu infra per customer | New topic/queue per cloud | One SQS queue per consumer |
  | Org isolation | Filter per topic (complex) | JWT org claim (simple) |
  | Future customer new cloud | New SDK to build | Zero change |
  | Vendor neutral? | NO — tied to each cloud SDK | YES — plain HTTPS |
  | Egress cost | Cross-cloud data transfer | Internal AWS only |

  Bottom note (red): "RECOMMENDATION: SNS/SQS stays internal to Habu.
                      External partners always receive via HTTP (Approach 2).
                      Approach 3 only if a large enterprise contractually prohibits inbound HTTPS."

=== RIGHT STRIP — When Approach 3 makes sense (teal) ===

Title: "When Approach 3 is the right call"
  Scenario 1: "Internal consumers within Habu AWS account — zero complexity"
  Scenario 2: "Enterprise contract: customer prohibits inbound HTTPS — negotiate as premium tier"
  Scenario 3: "Hybrid (recommended): SNS/SQS internal bus → HTTP delivery worker → HTTPS to consumer
               SNS IS the internal bus. HTTP IS the external interface. Best of both."

COLOR: Blue = mutations, Purple = interceptor, Orange = SNS + GCP path,
Yellow = Azure path, Red = complexity warnings, Teal = decision guidance, Green = Activity Feed.
Make red complexity boxes PROMINENT — they are the key decision input for this diagram.
```
