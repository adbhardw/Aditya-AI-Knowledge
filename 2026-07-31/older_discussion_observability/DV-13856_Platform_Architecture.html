The Problem

Clean room objects change — nobody outside Habu knows

External systems (XMI UI, customer integrations) poll API endpoints every N seconds. There is no notification mechanism. Three object domains are affected today, with more as Habu grows.

📋 Questions · unhygienix

Question Changes Go Unnoticed

When output columns are removed, a dataset is swapped, or a question is deleted, XMI UI has no way to know until its next poll cycle. Downstream dashboards and workflows break silently.

🔌 Data Connections · orbit

Schema Changes Break Pipelines

When a field type changes or fields are added/removed, downstream SQL queries and pipelines fail at runtime — no notification reaches dependent teams before the failure.

📤 Exports · picanmix

Export Status Is Invisible

Export configuration changes and run completions are invisible to integrations. External systems must poll repeatedly to detect whether an export finished, failed, or was reconfigured.

⚡

Scope beyond DV-13856: This is not a one-off XMI notification feature. The same gap exists for every programmatic consumer of the Habu API. Building it right means a reusable event infrastructure that plugs into any Habu service going forward.

Five services. One event infrastructure.

The interceptor + event bus + delivery pattern is built once and plugs into every Habu service. Each service emits standardised events — any consumer can subscribe without changing the source service.

Phase 2 Decision

Event bus infrastructure: AWS SNS vs GCP Pub/Sub

Both are viable. The choice affects Phase 2 operational complexity and delivery model. Phase 1 (DB table + UI) is infrastructure-agnostic and ships first regardless.

Criterion AWS SNS + SQS GCP Pub/Sub
Already in platform? YES — picanmix already uses SNS + hank library NO — new GCP dependency to add
HTTP delivery (no extra worker) NO — must build SQS consumer worker to POST to URLs YES — Pub/Sub Push Subscriptions deliver HTTP natively
Custom auth on outbound POST YES — worker controls auth header (Bearer/API Key/Basic) PARTIAL — OIDC token only; custom auth needs proxy
Built-in retry + DLQ YES — SQS visibility timeout + SQS DLQ YES — configurable retry policy + dead-letter topic
Message ordering YES — FIFO SNS/SQS (picanmix uses .fifo already) YES — ordering keys per subscription
Operational overhead Medium — SQS consumer worker service to manage Low (push mode) — Pub/Sub manages delivery itself
Platform fit HIGH — consistent with existing unhygienix/picanmix pattern Low — introduces multi-cloud complexity
Recommendation — AWS SNS + SQS

SNS is already wired in picanmix via the hank library. SQS gives us retry + DLQ with no new infrastructure. The consumer worker gives us full control over auth and payload shaping. Consistent with how the rest of Habu handles async events.

When GCP Pub/Sub Makes Sense

If Habu becomes multi-cloud and GCP services need to subscribe to events, Pub/Sub's native push subscriptions simplify delivery. Defer this unless the platform explicitly moves multi-cloud — the SNS/SQS approach can be swapped behind the event bus interface without changing the interceptors or delivery worker logic.

Design Decisions

Key questions answered

Q: Why write to a DB table — can't the UI read queue (SNS/SQS) data directly?
A message queue is designed for one-time delivery — a consumer reads a message, processes it, the message is deleted. There's no persistent history. If you want a UI showing "what happened in the last 30 days," queue data is already gone by then.

The object_events table is a persistent, queryable ledger — always there, filterable by date/user/type, never expires until the retention policy fires. The queue (SNS → SQS) is used for webhook delivery in Phase 2 only — fire-and-forget to external endpoints. Think of it: the table is the record book; the queue is the postal service.
Q: Why not use GCP Pub/Sub push subscriptions — wouldn't that eliminate the delivery worker?
Pub/Sub push does eliminate the worker for basic delivery, but it limits authentication to OIDC tokens only — you can't attach a custom Bearer token or API key without adding a proxy in front. Enterprise customers often require specific auth headers. Additionally, SNS is already wired into picanmix via the hank library, so Phase 2 reuses existing platform plumbing. The event bus interface in the design is abstracted — we can swap SNS → Pub/Sub later without touching interceptors or the delivery worker logic.
Q: Can the interceptor / event infrastructure scale to other Habu services beyond the three in scope?
Yes — that is the point of building it as platform infrastructure, not a one-off feature. The MutationInterceptor interface is a contract any service implements. The event bus, object_events table, callback_registrations, and delivery worker are shared. Adding a new service (e.g., a future "catalogmix" or a new scheduler) means implementing the interceptor in that service and pointing it at the same SNS topic. No changes to the delivery layer.
Q: What is the "webhook server" on the XMI side that we need?
For Phase 2 callbacks, XMI UI needs to expose an HTTPS endpoint that Habu's delivery worker POSTs to. That is their "webhook server" — a small receiver that accepts Habu's JSON payload and reacts (refresh cache, update UI, trigger downstream workflow).
Phase 1's cursor API (GET /cleanrooms/{'{id}'}/events?since=T) avoids this requirement entirely — XMI calls Habu on their schedule instead of maintaining an inbound server. Recommended as XMI's near-term path, with Phase 2 push webhooks as the long-term model.

Phase 2 adds push-based notification for programmatic consumers. Once a callback URL is registered, Habu automatically calls it when a monitored object changes. Delivery is fully async (SNS → SQS → Event Listener Job → Delivery Worker) — the user's mutation never waits for the external endpoint. Failed deliveries retry up to 3× with exponential backoff. Undeliverable events land in a Dead Letter Queue for review. The same infrastructure serves XMI today and any new consumer in the future.
