DV-13856 — Cleanroom Observability: Event Notification Design

Mirro : Design :  https://miro.com/app/board/uXjVHLcSxuI=/?share_link_id=244206250371

Problem
Cleanroom consumers—starting with XMI and expanding to future partners—currently have no standardized way to know when objects inside a cleanroom change.

Examples include:

A data connection moves from  CONFIGURATION_COMPLETE to Deleted.

A question's SQL is modified

An export job destination changes

Today, consumers learn about these changes through:

Manual communication

Polling individual resource endpoints

This creates:

Delayed downstream reactions

Broken workflows

Increased support overhead

The goal is to build a first-class event notification layer that captures all cleanroom object mutations and exposes them through a structured, reliable, cloud-agnostic interface.

What We Are Building
The observability solution consists of three major components.

1. Event Capture
Every mutation to:

QUESTION

DATA_CONNECTION

EXPORT_JOB

is captured as an immutable event row inside a centralized append-only table:



object_events
stored in the Unhygienix/New Service (later discussed) database.

Each event contains a structured diff:



{
"field": {
"from": "<old-value>",
"to": "<new-value>"
}
}
Schema: CNCF CloudEvents
The event schema is based on CNCF (Cloud Native Computing Foundation) CloudEvents v1.0, the industry-standard specification for event-driven systems.

CloudEvents is widely adopted across the industry and serves as the foundation for event delivery in platforms such as:

Stripe Events

GitHub Webhooks

Salesforce Platform Events

AWS EventBridge

Google Eventarc

Azure Event Grid

By adopting CloudEvents, We align with a well-known standard that engineering teams already understand. Consumers do not need to learn a proprietary LiveRamp-specific event envelope, and integrations can leverage existing tooling, SDKs, and event-processing frameworks.

CloudEvents Envelope


{
"specversion": "1.0",
"id": "<event-uuid>",
"source": "urn:habu:cleanroom:<cleanroom-id>",
"type": "com.habu.cleanroom.<object-type>.<action>",
"time": "<RFC3339 UTC timestamp>",
"data": {
"objectType": "<QUESTION | DATA_CONNECTION | EXPORT_JOB>",
"objectId": "<uuid>",
"objectName": "<name at time of event>",
"changeType": "<CREATED | UPDATED | DELETED>",
"changedFields": {
"<field>": {
"from": "<old-value>",
"to": "<new-value>"
}
},
"performedBy": "<user-email or system:service-name>",
"schemaVersion": 1
}
}
Why CloudEvents
1. Industry Standard
CloudEvents has become the de facto standard for event exchange across modern cloud platforms and SaaS ecosystems.

Consumers already understand concepts such as:

id

source

type

	time

which reduces onboarding effort and minimizes custom integration code.

Example event type:



com.habu.cleanroom.data_connection.updated
The reverse-DNS naming convention is consistent with patterns already used across the industry.

2. Vendor Neutral
CloudEvents is supported natively across all major cloud providers:

AWS EventBridge

Google Eventarc

Azure Event Grid

Cloud infrastructure uses the standard CloudEvents metadata fields:

specversion

source

type

for routing, filtering, and subscription management, while LiveRamp’s business payload remains inside the data section.

As a result:

XMI on GCP

Microsoft on Azure

Future consumers on any cloud

all receive the exact same payload without cloud-specific transformations.

3. Delivery Model Independence
The schema is completely independent of the delivery mechanism.

The same CloudEvents payload can be delivered through:

Pull APIs

Webhooks

Cloud-native queues

Changing delivery models does not require:

Schema changes

Database changes

API contract changes

This allows Habu to introduce additional delivery mechanisms over time without impacting existing consumers.

4. Consistent Change Representation
Every object type uses the same changedFields structure:



{
"field": {
"from": "<old-value>",
"to": "<new-value>"
}
}
Examples:



{
"changedFields": {
"stage": {
"from": "MAPPING_REQUIRED",
"to": "CONFIGURATION_COMPLETE"
}
}
}


{
"changedFields": {
"sqlQuery": {
"from": "SELECT ... WHERE amount > 100",
"to": "SELECT ... WHERE amount > 50"
}
}
}


{
"changedFields": {
"destination": {
"from": "s3://a/a.bcs",
"to": "s3://b/b.abc"
}
}
}
Because every change follows the same { from, to } pattern, consumers can process all object types using a single parsing model without branching logic for specific resources.

Why This Works
Pegleg already communicates with unhygienix through gRPC.

Activity Feed is fundamentally a cleanroom concept.

external-api-server already depends heavily on unhygienix.

No additional service deployment is required.

Trade-offs
Pros

Lowest implementation cost.

No additional infrastructure.

No new service ownership.

Cons

Pegleg becomes responsible for event routing despite observability being outside its domain.

unhygienix grows observability responsibilities.

Event-store schema changes require migrations inside the largest service in the platform.

Future observability features further increase coupling.

Architectural Recommendation
MVP Recommendation
Option A (Pegleg → unhygienix)

Advantages:

Lowest implementation cost

Fastest path to production

Reuses existing infrastructure

Enables Activity Feed immediately


Option B (orinix)

Observability is a cross-cutting concern that naturally expands into:

Delivery logs

Webhook registrations

Callback workers

Retry infrastructure

Consumer-specific delivery policies

Keeping those concerns isolated prevents unhygienix from becoming the owner of unrelated platform functionality.

As the observability platform grows, Option B provides cleaner ownership boundaries and lower long-term maintenance cost.

Not recommended as the default integration model.
