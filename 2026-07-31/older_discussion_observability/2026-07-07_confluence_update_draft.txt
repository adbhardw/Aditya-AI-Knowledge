================================================================================
1. DELIVERY REGISTRATION — delivery_type and delivery_config
================================================================================

A single callback_registrations table serves both delivery mechanisms. One row
per consumer per cleanroom+object type; a consumer may register BOTH
mechanisms at once (two rows) for the same cleanroom+object type.

  Column           Type      Notes
  ---------------- --------- ---------------------------------------------
  delivery_type    VARCHAR   "WEBHOOK" or "PUBSUB" — the discriminator
  delivery_config  JSONB     Shape depends on delivery_type (see below)
  signing_secret   VARCHAR   HMAC-SHA256 secret, WEBHOOK only

delivery_config shape by delivery_type:

  WEBHOOK:
    { "callback_url": "https://events.xmi.liveramp.com/habu-webhook" }

  PUBSUB:
    { "gcp_project_id": "xmi-prod-12345", "gcp_topic_id": "habu-cleanroom-events" }

Example: XMI registering for both mechanisms on the same cleanroom+object type
produces two independent rows:

  Row 1: delivery_type=WEBHOOK, delivery_config={"callback_url": "..."}
  Row 2: delivery_type=PUBSUB,  delivery_config={"gcp_project_id": "...", "gcp_topic_id": "..."}

Both are delivered to independently for every matching event — registering
for one does not require choosing between them.

================================================================================
2. IDEMPOTENCY
================================================================================

The idempotency key is the CloudEvents envelope's own `id` field (a UUID),
minted ONCE by the producing service (unhygienix / forebitt / picanmix) at the
moment of the real mutation — not derived from any table columns, not
generated by orinix.

Producer responsibility: if a publish attempt to SNS fails or times out and
the producer retries, it MUST reuse the same `id` on the retry, not mint a
new one. This is the one rule that makes everything downstream work.

Propagation — the same id is used at every stage, unchanged:

  Producer mints id -> SNS -> SQS -> object_events.idempotency_key
  (orinix's own dedup, UNIQUE constraint) -> X-Habu-Event-Id header on every
  webhook delivery (XMI dedup) -> Pub/Sub message attribute on every PUBSUB
  delivery (equivalent dedup for Pub/Sub consumers)

Consumer responsibility (both WEBHOOK and PUBSUB): delivery is at-least-once,
never exactly-once. Consumers MUST deduplicate on this id before processing —
receiving the same id twice means "the same event, delivered again," not "two
events."

Defense-in-depth (optional, not required for M1): a secondary deterministic
fingerprint (hash of cleanroom_id + object_id + change_type + changed_fields)
as a backup uniqueness check at ingest, for the unlikely case a producer fails
to preserve its own id across a retry.

================================================================================
3. WEBHOOK SIGNING — HMAC-SHA256, symmetric
================================================================================

Webhook payloads are signed, not encrypted. This uses a SYMMETRIC scheme
(HMAC-SHA256) — one shared secret, identical on both Habu's and the
consumer's side. This is the same approach used by Stripe (Stripe-Signature)
and GitHub (X-Hub-Signature-256) — industry standard for webhook delivery,
not a custom scheme.

  signing_secret: minted once at registration time (e.g. "whsec_9f8e7d6c...").
  Returned exactly once, in the RegisterCallback response.

Delivery headers on every webhook POST:

  Content-Type:      application/cloudevents+json
  X-Habu-Signature:  <hex-encoded HMAC-SHA256 of the raw payload, using signing_secret>
  X-Habu-Event-Id:   <the CloudEvents id — see Idempotency above>

Consumer verification: recompute HMAC-SHA256(payload, signing_secret) and
compare to X-Habu-Signature. A mismatch means the payload was altered or did
not originate from Habu.

Security note: because this is symmetric, signing_secret is exactly as
sensitive on the consumer's side as on ours — a leak on either end allows
forged, signed payloads. Consumers should store it as a credential, not a
config value.

================================================================================
4. DLQ / RETRY POLICY
================================================================================

Per-consumer delivery queues (e.g. sqs-habu-delivery-xmi) use SQS's native
redrive policy — this is Habu's own responsibility end-to-end; consumers are
never involved in retry/failure handling.

  Retry attempts:     5 (maxReceiveCount)
  Backoff:            increasing visibility timeout between attempts
                       (exponential, with jitter)
  On exhaustion:      message moves automatically to a linked DLQ

Post-DLQ handling (Habu-internal, not consumer-facing):
  - CloudWatch alarm on DLQ depth > 0 pages Habu on-call (not the consumer)
  - On-call inspects the failed message, confirms root cause resolved (e.g.
    consumer endpoint back up), replays via SQS's native redrive-to-source
  - Consumers receive no direct failure signal for M1 — open question
    whether a future milestone adds one

================================================================================
5. object_events SCHEMA (unchanged from v6, restated for completeness)
================================================================================

  Column            Type          Notes
  ----------------- ------------- --------------------------------------
  id                UUID          primary key
  spec_version      VARCHAR(10)   CloudEvents spec version, default 1.0
  source            VARCHAR       urn:habu:cleanroom:{cleanroom_id}
  type              VARCHAR       com.habu.cleanroom.<object_type>.<action>
  org_id            UUID          for org-scoped isolation
  cleanroom_id      UUID          for cleanroom-scoped pull queries
  object_type       VARCHAR       QUESTION | DATA_CONNECTION | EXPORT_JOB | FLOW | FLOW_RUN
  object_id         UUID          the mutated object's id
  object_name       VARCHAR       snapshot at event time (survives deletion)
  change_type       VARCHAR       CREATED | UPDATED | DELETED | STATUS_CHANGED
  changed_fields    JSONB         { "field": { "from": X, "to": Y } }, uniform across all object types
  performed_by      VARCHAR       user email or "system:<service-name>"
  schema_version    INT           default 1
  idempotency_key   VARCHAR       UNIQUE — see Idempotency section above
  cursor_position   BIGSERIAL     global monotonic sequence, NOT per-cleanroom
                                  (queries filter by cleanroom_id + cursor_position together)
  event_time        TIMESTAMPTZ   default NOW()

Append-only, enforced at the DB level (REVOKE UPDATE, DELETE), not just by
application convention.
