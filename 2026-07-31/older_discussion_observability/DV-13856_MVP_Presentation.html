The Problem

No notification system exists for clean room object changes

External systems poll GET /cleanrooms/{id}/questions every N seconds. Most calls return "nothing changed." When something does change, the reaction is delayed and the diff is imprecise.

📋 Questions

Question Changes Go Unnoticed

When output columns are removed, a dataset is swapped, or a question is deleted, XMI UI has no way to know until its next poll cycle. Downstream dashboards and workflows break silently.

🔌 Data Connections

Schema Changes Break Pipelines

When a field type changes (Integer → String) or fields are added or removed, SQL queries and data pipelines fail at runtime with no prior warning to dependent teams.

📤 Exports

Export Status Is Invisible

Export configuration changes and run completions are invisible to integrations. External systems must poll repeatedly to detect whether an export finished, failed, or was reconfigured.

⚡

Root cause: No event notification system exists for clean room objects. Every external consumer is forced to poll and run their own diff. The platform does not tell you when something changed — you have to go ask.

Solution

One foundation. Two consumers.

A single interceptor fires on every create/update/delete and writes to a persistent event store. V1 reads that store for the UI. V2 uses a queue for push delivery to external endpoints.

Shared Foundation — Interceptor (unhygienix)
On any create / update / delete in unhygienix:
  1. Snapshot before state of the object
  2. Execute the mutation
  3. Compute diff (before vs. after)
  4. Write event row to object_events table     V1
  5. If callback registered → publish to SNS V2

Design Decisions

Key questions answered

Q: Why write to a database table — can't we show the UI using queue (SNS/SQS) data directly?
A message queue is designed for one-time delivery — a consumer reads a message, processes it, and the message is deleted. There's no persistent history to query.

If you want a UI that shows "what happened over the last 30 days," the queue data is already gone. The object_events table is a persistent, queryable ledger — always there, filterable by date/user/type. The queue (SNS → SQS) is used for webhook delivery in V2 only — fire-and-forget to external endpoints.

Think of it this way: the table is the record book. The queue is the postal service.
Q: For MVP event display — do we need to show deep data like "SQL changed at line 3"?
No — not for MVP. The high-level summary ("Output columns were modified by sarah@acme.com on May 9") is sufficient for audit and answers the key question: did something change, who did it, when?

The detailed field-level diff (exact columns removed, exact type changes) is stored in the changed_fields JSONB column and can be exposed on-click in V2/V3. For MVP, the summary label gives users enough context without overloading the feed — this is a pragmatic tradeoff.
Q: What is a "webhook server" on the XMI side?
For V2 callbacks, XMI UI needs to expose an HTTPS endpoint that Habu can POST to when objects change. That endpoint is their "webhook server" — a small receiver that accepts Habu's JSON payload and reacts (refresh UI, update cache, trigger workflow).

V1's cursor-based polling API (GET /cleanrooms/{'{id}'}/events?since=T) avoids this requirement entirely — XMI calls Habu's API on their own schedule instead of maintaining an inbound server. This is the recommended near-term path for XMI, with V2 webhooks as the long-term push model.

V2 Summary — Webhook Callback Delivery

V2 adds push-based notification for programmatic consumers. Once a callback URL is registered via POST /cleanrooms/{'{id}'}/callbacks, Habu automatically calls that URL when a monitored object changes — sending the object name, change type, who changed it, and when. Delivery is fully async (SNS → SQS → worker), so the user's mutation never waits for the external endpoint. Failed deliveries retry up to 3× with exponential backoff; undeliverable events go to a Dead Letter Queue.
