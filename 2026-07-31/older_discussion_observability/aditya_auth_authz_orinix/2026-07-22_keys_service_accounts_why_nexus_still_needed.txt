WHERE THE KEYS ACTUALLY LIVE, WHY A SERVICE ACCOUNT IS NEEDED, AND WHY
DECENTRALIZED VERIFICATION DOESN'T MAKE NEXUS REDUNDANT
Follow-up to 2026-07-22_jwks_mechanism_and_who_actually_uses_authnproxy.txt
Date: 2026-07-22


===========================================================
0. FIRST, UNTANGLE TWO DIFFERENT SECRETS THAT LOOK SIMILAR
===========================================================

This is probably the root of the confusion, so separate it out clearly.
There are TWO completely different secrets in play, owned by two different
things:

  (a) THE SERVICE ACCOUNT'S OWN CREDENTIAL
      A long-lived credential file identifying "this is service X" (e.g.
      MCS's own credentials.json). Lives in Vault. Mounted into THAT
      service's access-token-getter sidecar only. Used to ASK Nexus for a
      fresh access token ("Obtain Access Token" use case). This is like a
      login password for the app itself.

  (b) THE SIGNING KEY
      The cryptographic key pair used to cryptographically STAMP every
      issued token so it can't be forged. This has nothing to do with any
      individual service. There is ONE such key pair (rotated every 24h),
      and it belongs to Nexus's own "Service Account Authenticator"
      component, not to any calling app.

Different secret, different owner, different purpose. MCS never sees or
holds (b) at all.


===========================================================
1. WHERE DOES THE PRIVATE KEY LIVE? WHERE'S THE PUBLIC KEY?
===========================================================

Private key: Google Secret Manager ("Signing key storage" in the diagram).
  ONLY Nexus's "Service Account Authenticator" component ever reads it, to
  sign a newly-issued token. It NEVER leaves Nexus. No sidecar, no app, no
  authn-proxy ever has access to it. This is the actual root of trust — if
  you don't have this key, you cannot mint a token that anyone will accept,
  full stop.

Public key: fetched by authn-proxy from Nexus's "Get Verification Keys"
  (JWKS) endpoint, then held in memory (cached) INSIDE that authn-proxy
  sidecar. Not stored in Vault — it doesn't need Vault-level protection,
  because a public key being public is fine by design (that's the entire
  point of asymmetric crypto — anyone can safely hold the public half,
  only the private half is dangerous to leak). It's just refreshed
  periodically from Nexus (roughly matching the 24h rotation cadence) and
  kept in the sidecar's memory in between.

So: private key never leaves Nexus. Public key gets copied out to every
verifying sidecar's local cache, safely, because it's meant to be public.


===========================================================
2. WHY IS A SERVICE ACCOUNT NEEDED AT ALL?
===========================================================

Because an app has no identity of its own by default. A human has a login;
an app calling another app needs SOME name to present, or every check
downstream ("who did this," "is this identity allowed to do X," "who do we
blame in an audit log") has nothing to attach to.

The service account IS that identity — the machine equivalent of a user
account. It exists so that:
  - CAC has something concrete to check a permission against ("does
    service-account-MCS hold this permission" instead of "does <nothing>
    hold this permission").
  - Audit logs can say "MCS did this," not "someone did this."
  - Access can be granted/revoked to ONE specific caller (MCS) without
    affecting any other caller — you couldn't scope trust that precisely if
    every app just shared one anonymous "machine" identity.

Without it, verification could still mathematically work (you could sign
tokens for "anyone"), but authorization couldn't — CAC's whole job is
answering "does THIS identity hold THIS permission," and there'd be no
"this identity" to ask about.


===========================================================
3. "IF IT CAN DO EVERYTHING INDEPENDENTLY, WHY IS NEXUS STILL NEEDED?"
===========================================================

Because the sidecars are NOT independent authorities — they're caches and
proxies IN FRONT OF Nexus, not replacements for it. What decentralizes is
narrow and specific: verifying a signature you already have, using a public
key you already cached. That's it. Everything else still goes through
Nexus, every time:

  - Getting a BRAND NEW token in the first place — access-token-getter still
    has to call Nexus's Authenticator directly ("Obtain Access Token"); it
    only caches the RESULT for a few minutes (300s per the agentic-core
    docs), it doesn't generate tokens itself.
  - Creating, deleting, enabling/disabling a service account at all — only
    Nexus's Service Account Manager can do this. No sidecar can mint a new
    identity out of thin air.
  - Refreshing the public key set used for verification — sidecars fetch
    this FROM Nexus periodically; they don't generate their own keys.
  - The actual PERMISSION decision (CAC) — always a live call, never
    cached/local, because permission grants can change at any moment and
    staleness there is a real security risk (unlike a signature, which is
    either mathematically valid or it isn't, forever, for that specific
    token).

Good analogy: this is exactly like a CDN in front of a website. The CDN
doesn't make the origin server unnecessary — it just avoids hitting the
origin for the same static content over and over. The origin is still the
one and only source of truth; the CDN is a performance optimization layered
on top. Nexus is the origin. authn-proxy's local JWKS cache is the CDN
layer, for exactly one narrow operation (signature verification) that
happens to be safe to cache because of how asymmetric crypto works.


===========================================================
4. "IS authn-proxy THE ONE THAT VALIDATES THE TOKEN LOCALLY?"
===========================================================

Yes, confirmed directly — that is its entire job. Take the incoming Bearer
token, check its signature against the cached public key, and if valid,
decode it and stamp the verified identity onto the `X-Validated-Access-Token`
header before the request reaches the app. Nothing more.


===========================================================
5. "WHY CAN'T THE SAME SERVICE THAT ISSUED IT ALSO VERIFY IT?" (i.e. why
   not have every service call Nexus to check each token, like CAC does)
===========================================================

It CAN — that's literally what the centralized model (moonraker, or how CAC
handles it for MCS) does: every verification is a round-trip back to the
issuer/authority. Nothing technically prevents that.

The reason LiveRamp built the alternative isn't "the issuer can't verify its
own tokens" — it's that it doesn't NEED to, because of how signed tokens
work: anyone holding the public key can verify a signature without ever
talking to the signer again. That's the whole mathematical point of
public/private key signing (unlike, say, a plain shared-secret API key,
which genuinely does require the issuer to be the one checking it, since
there's no separate "public half" to hand out safely).

So routing every single verification back through Nexus would be
technically fine but WASTEFUL — it turns Nexus into a mandatory hop for
every request in the entire company, for a check that doesn't actually
require Nexus's involvement each time. Decentralizing verification removes
that unnecessary traffic from Nexus's critical path, with zero loss of
security: a forged token still fails the local signature check, because
producing a valid signature still requires the private key, which never
left Nexus.


===========================================================
6. "WHY IS USING CAC-ONLY (NO LOCAL VERIFY SIDECAR) BETTER FOR AN INTERNAL
   SERVICE?" — not a corner-cutting compromise, here's the actual reasoning
===========================================================

"Better" here doesn't mean "more secure" — both approaches are equally
secure (CAC still does real verification, just over the network instead of
locally). "Better" means better ENGINEERING TRADEOFF for that specific
service's actual traffic profile:

  - Lower, more predictable volume. An internal-only service is called only
    by a small, known set of other internal services — not the open
    internet. The downside of the centralized approach (per-request network
    hop, load on the central service) scales with request volume, and
    internal-to-internal traffic is typically a small fraction of what a
    public endpoint sees.
  - Already inside a trust boundary. It's reachable only via
    cluster-internal DNS — there is no path for random/adversarial internet
    traffic to reach it at all. A public endpoint has to defend against
    arbitrary junk/attack traffic and wants to reject it as cheaply as
    possible (ideally without even finishing a network round-trip);
    an internal endpoint doesn't face that threat model at anywhere near the
    same volume.
  - Less operational cost. No extra sidecar container to deploy, patch, keep
    healthy, and monitor, and no local key-caching machinery to get right.
    For modest, trusted, internal traffic, that complexity buys you very
    little.

So the tradeoff genuinely tips the other way for internal-only, modest-
volume traffic: pay the (small, acceptable-at-that-volume) cost of a network
hop to CAC, and skip an entire extra piece of infrastructure you don't get
much benefit from at that scale. That's exactly why msb-langgraph-server
(internal-only) skips authn-proxy while msb-api (externally reachable, same
team) keeps it — and it's the same reasoning that applies to
orinix -> XMI, if XMI's callback endpoint is only ever called by orinix and
other internal LiveRamp services rather than being open to the public
internet.
