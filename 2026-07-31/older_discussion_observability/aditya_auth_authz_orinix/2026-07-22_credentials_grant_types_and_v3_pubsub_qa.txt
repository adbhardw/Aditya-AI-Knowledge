Q: What does credentials.json actually contain — client_id/secret, or
   username/password?
===========================================================

A: Both, but not in the way you'd expect — `client_id` is NOT per-service.
Confirmed from the real example in
infra_api_platform/docs/calling-authenticated-apis.md:

    {
      "type": "serviceAccount/v1",
      "uid": "00u1nmeo9zo99s233357",
      "account_id": "test-mukqxb57@serviceaccounts.liveramp.com",
      "secret_key": "vdmAe8Pzxf6lW5-tYEeqmKbV167NCnkdhUqs-KBg1t4",
      "client_id": "liveramp-api",
      "token_uri": "https://sso.liveramp.com/oauth2/default/v1/token"
    }

  - `account_id` = the "username" — an email-shaped identity, unique per
    service account (e.g. would be something like
    `orinix-sa@serviceaccounts.liveramp.com`).
  - `secret_key` = the "password" — a random opaque secret string.
  - `client_id` = a FIXED constant (`"liveramp-api"`), the same value for
    every single LiveRamp service account. Not a per-service identifier —
    just says "this request is going through the standard LiveRamp API
    client."
  - `uid` = a stable internal ID, separate from the human-readable
    `account_id`.
  - `token_uri` = self-describing — tells the token-getter exactly where to
    POST this to get a token.
  - `type` = distinguishes v1 (`sso.liveramp.com`) vs v2
    (`serviceaccounts.liveramp.com`) service account generations.

Schema reference: github.com/LiveRamp/nexus/blob/master/schemas/service-account.jsonnet

Provisioning path (from the same doc): create via the CAC-alpha UI, or file
an OC ticket to component "AAA: Authentication and Access Team" if
self-service isn't available. One service account per application (not one
per API you call) — application owns its own SA name.

Q: What are the different OAuth2 grant types, and which does Nexus use?
===========================================================

A: Standard OAuth2 grant types, general reference:
  - authorization_code — human login via browser redirect; interactive.
  - client_credentials — the CONVENTIONAL machine-to-machine grant:
    client_id + client_secret, no human, no username/password fields.
  - password (Resource Owner Password Credentials) — raw username+password
    sent directly to the token endpoint; considered legacy in modern OAuth2
    guidance.
  - refresh_token — exchange a previously-issued refresh token for a new
    access token without resending the original credential.
  - device_code / implicit — device-constrained flows / deprecated
    browser-only flow, not relevant here.

WHAT NEXUS ACTUALLY USES, mapped to real evidence:
  - Service accounts (orinix/MCS/VMA) -> `password` grant. Confirmed via
    apps/service-account/apps/authenticator/pkg/handler/oauth2/password_grant.go
    (`grant_type=password&username=...&password=...&client_id=...`).
    NOTABLE: this is a deliberate choice, not an oversight — confirmed via
    password_grant_test.go, which explicitly asserts that setting
    `grant_type=client_credentials` on this endpoint returns
    `unsupported_grant_type`. Nexus's service-account authenticator only
    accepts `password`, even though `client_credentials` is the more
    conventional grant for machine identities elsewhere in the industry.
    `account_id`/`secret_key` just play the username/password role instead.
  - Human personal tokens (`lrtoken` CLI) -> `authorization_code` grant
    (liveramp-token-fetcher/pkg/oidc/oidc.go: AUTH_CODE_GRANT_TYPE).
  - Renewing an already-issued token -> `refresh_token` grant
    (liveramp-token-fetcher/pkg/cache/cache.go).

So orinix's actual token request will be:
  grant_type=password&username=<account_id>&password=<secret_key>&client_id=liveramp-api

Q: What's the actual difference between "Static Shared Secret" and
   "Signed JWT Only" (the two rejected/insufficient options)?
===========================================================

A: Not "static = the OAuth token, signed JWT = shared key pair" — both
halves of that framing needed correcting.

  Static Shared Secret:
    - One fixed string, agreed upon in advance, out of band. Never expires
      unless manually rotated. NOT obtained via any OAuth flow at all —
      it bypasses issuance entirely, just pre-exists on both sides.
    - Carries no identity, no structure, no expiry — verification is a
      plain string comparison ("does this match what I have stored").
    - If leaked: full impersonation, forever, everywhere it's used, until
      manually rotated on both sides.

  Signed JWT:
    - Freshly issued, expiring, structured token, minted on demand by an
      issuer (Nexus). Verification is a cryptographic signature check, not
      a string comparison.
    - Key material is ASYMMETRIC, not shared: Nexus alone holds the
      PRIVATE key (signs); every verifier only ever holds the PUBLIC key
      (verifies). "Shared" is the wrong word — the whole point is that only
      one side ever has anything dangerous to leak.
    - If leaked: only usable until it expires (minutes), and a leaked
      token can't be used to mint further tokens.

  | | Static Shared Secret | Signed JWT |
  |---|---|---|
  | Issued by | nobody, pre-shared | central issuer (Nexus), on demand |
  | Encodes identity | no | yes (claims) |
  | Verified how | string compare | cryptographic signature check |
  | Key material | same secret on both sides | private stays at issuer; public distributed safely |
  | If leaked | permanent, until manual rotation | expires in minutes |

  WHY "signed JWT only" was STILL marked insufficient (separately from
  static secret): a signed JWT fixes identity (you now know cryptographically
  WHO is calling) but still answers nothing about WHAT they're allowed to
  do. That's exactly why the final recommendation isn't "just sign
  tokens" — it's signed JWT (Nexus, for identity) PLUS CAC (for the
  separate permission decision). Static secret fails at both; signed-JWT-
  only fixes one but not the other.

Q: For V3 (Cloud-Native Queue / Pub/Sub) — is there a real precedent in our
   OWN ecosystem, not just LiveRamp's separate billing team?
===========================================================

A: Yes — Pegleg itself already publishes to Pub/Sub. This is a better,
more directly relevant precedent than LiveRamp's billing_service (a
different company, different codebase) because Pegleg is IN the same
Habu/Cleanroom ecosystem as orinix.

Source: pegleg-backend/src/main/java/com/habu/pegleg/billing/
BillingMessagePublisherHelper.java

  public Publisher getPublisher() throws IOException {
      BillingTopicInfo topicInfo = getBillingTopicInfo();
      Credential.GetBillingTopicCredentials.Response response =
          primageClient.getBillingTopicCredentials();
      String jsonKey = TeeUtil.getGoogleAuthCredentialsJson(response.getCredentials());
      GoogleCredentials credentials = GoogleCredentials.fromStream(
          new ByteArrayInputStream(jsonKey.getBytes(StandardCharsets.UTF_8)));
      TopicName topicName = TopicName.of(topicInfo.projectId(), topicInfo.topicId());
      return Publisher.newBuilder(topicName)
          .setCredentialsProvider(FixedCredentialsProvider.create(credentials))
          .build();
  }

Real topic/project targets (getBillingTopicInfo(), env-switched):
  DEV:     project "liveramp-events-dev",  topic "billing_v2-raw-metrics"
  STAGING: project "liveramp-events-prod", topic "billing_v2-raw-metrics-staging"
  PROD:    project "liveramp-events-prod", topic "billing_v2-raw-metrics"

HOW IT AUTHENTICATES — genuinely different from everything else discussed
in this investigation:

  1. Pegleg does NOT hold a long-lived GCP service account key itself. It
     calls ANOTHER internal Habu service, Primage, via gRPC
     (`primageClient.getBillingTopicCredentials()`), which hands back the
     credentials JSON dynamically at runtime. (Primage functions here as
     a credential broker, similar in spirit to how Vault/Nexus work for
     the LiveRamp side, but this is Habu's own separate mechanism.)
  2. That JSON is fed straight into Google's own client library
     (`GoogleCredentials.fromStream(...)`), and the Pub/Sub `Publisher` is
     built with `FixedCredentialsProvider.create(credentials)`.
  3. Verification of this credential, at publish time, is done ENTIRELY by
     Google Cloud IAM — not Nexus, not CAC. This is a completely separate
     trust system from everything else discussed for the V2 (Webhook)
     approach.

WHY THIS DIRECTLY EXPLAINS THE EXISTING RISK NOTE ("Service Account changes
on their end for Pub/Sub can break the flow without any changes from our
end"):

  Pub/Sub trust lives in GCP IAM role bindings, on BOTH the publisher's and
  the subscriber's side, entirely OUTSIDE LiveRamp's own Nexus/CAC system.
  For the V2 Webhook model, LiveRamp fully owns and can audit the whole
  identity+permission relationship end to end (Nexus issues, CAC grants/
  revokes, all inside one platform we control). For Pub/Sub, if a consumer
  changes their own GCP project structure, rotates or deletes the service
  account that was granted subscriber access, or changes an IAM binding on
  their side — the pipe breaks, and we have zero visibility or control over
  that change, because it happened entirely inside a system we don't own.
  This is the concrete, mechanical reason the risk note is true, not just a
  generic caution.

WHAT THIS MEANS FOR THE PRESENTATION: V3 can now cite a real, in-ecosystem
precedent (Pegleg's own billing publisher) rather than only pointing at a
different company's team (LiveRamp billing). Same credential-broker pattern
("fetch GCP creds dynamically from an internal service, don't hardcode
them") is worth calling out as the right way to do it if V3 is ever
exercised for orinix — mirror Pegleg's Primage-based credential fetch rather
than hardcoding orinix's own GCP SA key into a config file.
