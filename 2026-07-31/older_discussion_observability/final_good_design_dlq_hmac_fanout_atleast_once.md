**Date:** 2026-05-12
**Context:** DV-13856 Clean Room Observability MVP — deep dive on each architectural guarantee

## 1. Fan-out — How It Is Ensured

**What it means:** One event published by unhygienix reaches multiple independent downstream systems
(XMI, SafeHaven, future customer C) without any of them interfering with each other.

**How it works:**
```
unhygienix publishes ONE message to SNS topic: habu-object-events

SNS automatically delivers a copy to every subscribed SQS queue:
  → SQS-XMI          (XMI's delivery queue)
  → SQS-SafeHaven     (SafeHaven's delivery queue)
  → SQS-CustomerC     (future queue, doesn't exist yet)

Each queue is fully independent:
  - XMI's queue being full/slow does NOT delay SafeHaven
  - If XMI's worker crashes, SafeHaven is unaffected
  - Messages in SQS-XMI are deleted only after XMI's worker ACKs them
```

**Implementation detail:**
- Create SNS topic once in picanmix (already exists for DV-13837 export flow)
- For each new downstream consumer: create new SQS queue + add SNS subscription
- Zero code change to unhygienix when adding a new consumer

**Adding a new consumer tomorrow:**
```
aws sns subscribe \
  --topic-arn arn:aws:sns:us-east-1:...:habu-object-events \
  --protocol sqs \
  --notification-endpoint arn:aws:sqs:us-east-1:...:SQS-SafeHaven
```
That is the entire integration change on the producer side.

**Why this is architecturally significant for TLM:**
This is not a "callback for XMI" — it is a platform-level event bus.
Any Habu service or external partner can subscribe. The producer (unhygienix) never needs to change.

## 2. Circuit Breaker — How It Is Ensured

**What it means:** If XMI's endpoint is down or returning 5xx consistently,
the worker stops hammering it. Protects XMI from a flood of failed requests
and protects our worker from wasting threads.

**How it works (Resilience4j library in Java):**
```
State machine per endpoint URL:

CLOSED (normal)
  → track last N calls
  → if failure rate > threshold (e.g. 50% over last 10 calls): → OPEN

OPEN (endpoint is broken — stop calling)
  → all calls immediately rejected (no HTTP attempt) for 60s cooldown
  → after cooldown: → HALF-OPEN

HALF-OPEN (testing if endpoint recovered)
  → allow 1 test call
  → if success: → CLOSED
  → if failure: → OPEN again
```

**Implementation:**
```java
CircuitBreaker cb = CircuitBreaker.ofDefaults("xmi-endpoint");

// Wrap the HTTP call
CheckedRunnable postCall = CircuitBreaker
    .decorateCheckedRunnable(cb, () -> httpClient.post(url, payload));

try {
    postCall.run();
    // success → ACK SQS message
} catch (CallNotPermittedException e) {
    // circuit is OPEN — log, don't retry, put back in queue
} catch (Exception e) {
    // actual failure → retry logic kicks in
}
```

**State stored:** In-memory per worker instance. For shared state across multiple
worker instances: use Redis with circuit state key per endpoint URL.

**What gets logged:** "endpoint https://xmi.../habu-events entered OPEN state —
5 consecutive 5xx responses. Cooldown 60s."

## 3. HMAC Signature Verification — How It Is Ensured

**What it means:** XMI can cryptographically verify that the HTTP POST they received
actually came from Habu and was not tampered with in transit.
Without this, anyone who knows XMI's callback URL could send fake events.

**How it works:**

**At registration time:**
```
POST /cleanrooms/{id}/callbacks
Response includes:
{
  "id": "cb-456",
  "signingSecret": "whsec_a3f9c2b1..."   ← generated by Habu, stored by XMI
}
```
Habu stores this secret (encrypted at rest) linked to the registration.
XMI stores it on their side.

**At delivery time (Habu worker):**
```
requestBody = JSON.serialize(event)
signature   = HMAC-SHA256(signingSecret, requestBody)

HTTP POST headers:
  Content-Type: application/json
  Authorization: Bearer eyJ...          ← auth token (who is calling)
  X-Habu-Signature: sha256=a3f9c2...    ← payload integrity proof
  X-Habu-Event-Id: evt-789-uuid         ← for idempotency (see section 6)
  X-Habu-Timestamp: 1715521200          ← prevent replay attacks
```

**At receipt time (XMI side):**
```
recomputed = HMAC-SHA256(storedSecret, receivedBody)

if recomputed != X-Habu-Signature header:
    return 401 Unauthorized  ← reject, something is wrong

if abs(now - X-Habu-Timestamp) > 300s:
    return 401  ← reject, this is a replayed old request

process event
```

**Why two headers (Authorization + X-Habu-Signature):**
- Authorization (Bearer token): proves WHO is calling (Habu's identity)
- X-Habu-Signature (HMAC): proves the BODY was not modified (payload integrity)
Different guarantees, both needed.

**Key: per-registration secret.** XMI's secret is different from SafeHaven's.
A compromised XMI secret cannot be used to forge events to SafeHaven.

## 4. Dead Letter Queue (DLQ) with Replay — How It Is Ensured

**What it means:** Events that could not be delivered after max retries are not silently dropped.
They land in a holding queue where ops can inspect and re-deliver them.

**How SQS DLQ works automatically:**
```
Main SQS Queue config:
  maxReceiveCount: 3          ← after 3 failed visibility timeout cycles
  redrivePolicy: → DLQ ARN    ← SQS automatically moves message here

No application code needed for this routing — SQS handles it natively.
```

**Retry sequence before DLQ:**
```
Attempt 1: immediate         → 5xx or timeout
  SQS visibility timeout expires (30s) → message reappears

Attempt 2: worker picks up   → 5xx or timeout
  SQS visibility timeout expires → message reappears

Attempt 3: worker picks up   → 5xx or timeout
  SQS receive count = 3 = maxReceiveCount
  → SQS moves message to DLQ automatically

Total time before DLQ: ~90s
```

**What the DLQ message contains:**
```json
{
  "originalPayload": { ...event... },
  "registrationId": "cb-456",
  "callbackUrl": "https://xmi.../habu-events",
  "firstFailedAt": "2026-05-12T10:00:00Z",
  "lastFailedAt": "2026-05-12T10:01:30Z",
  "failureReason": "Connection timeout after 10s",
  "attemptCount": 3
}
```

**Replay flow:**
```
Option A — AWS Console / CLI:
  aws sqs start-message-move-task \
    --source-arn arn:...:DLQ-XMI \
    --destination-arn arn:...:SQS-XMI

Option B — DLQ Admin UI (see section 7 below):
  Ops clicks "Replay" on a specific failed message
  Backend: moves message from DLQ back to main SQS queue
  Worker picks it up and retries delivery

Option C — Replay API endpoint:
  POST /admin/callbacks/{registrationId}/replay-dlq
  Replays all DLQ messages for a given registration
```

**CloudWatch alarm on DLQ:**
```
Alarm: DLQ-XMI ApproximateNumberOfMessagesVisible > 0
Action: SNS → PagerDuty / Slack alert to on-call
```
This means any delivery failure that exhausts retries pages someone within minutes.

## 5. Delivery Observability — How It Is Ensured

**What it means:** We can answer these questions at any time:
- "Was event evt-789 delivered to XMI? When? How long did it take?"
- "How many deliveries failed in the last 24h?"
- "Which endpoint has the worst success rate?"

**How it works — delivery_log table:**
```sql
CREATE TABLE delivery_log (
    id                UUID PRIMARY KEY,
    registration_id   UUID NOT NULL,          -- which callback registration
    event_id          UUID NOT NULL,          -- which object_events row
    attempt_number    INT NOT NULL,           -- 1, 2, 3
    http_status       INT,                    -- 200, 500, null (timeout)
    response_time_ms  INT,
    delivered_at      TIMESTAMPTZ,
    failure_reason    VARCHAR,                -- "timeout", "5xx: Internal Server Error"
    payload_hash      VARCHAR,               -- SHA256 of sent payload (audit)
    UNIQUE (registration_id, event_id, attempt_number)
);
```

**Worker writes to this table after every attempt (success or failure).**

**What the UI shows (per registered callback):**
```
Registration: cb-456 | XMI | QUESTION q-123

  ● Last delivery:  2026-05-12 10:32:15  ✓ 200 OK  (43ms)
  ● Success rate:   98.2%  (last 30 days)
  ● Failed:         3 events in DLQ

  Recent deliveries:
  evt-901  2026-05-12 10:32  ✓ 200  43ms
  evt-900  2026-05-12 09:15  ✓ 200  51ms
  evt-899  2026-05-11 14:00  ✗ 500  → DLQ  [Replay]
```

**Metrics emitted (CloudWatch / Datadog):**
```
habu.callback.delivery.success     (count, by registration_id)
habu.callback.delivery.failure     (count, by registration_id, reason)
habu.callback.delivery.latency_ms  (histogram, by registration_id)
habu.callback.dlq.depth            (gauge, by queue name)
habu.callback.circuit.open         (gauge, by endpoint_url)
```

## 6. At-least-once with Idempotency — How It Is Ensured

**What "at-least-once" means:**
SQS guarantees every message is delivered AT LEAST once. In rare cases
(network partition, worker crash after POST but before ACK), it may deliver
the same message twice. This means XMI could receive the same event twice.

**The guarantee + the problem:**
```
Delivery worker:
  1. Read message from SQS       ← message now invisible (visibility timeout: 30s)
  2. POST to XMI → 200 OK        ← XMI received it
  3. Worker crashes before ACKing ← SQS visibility timeout expires
  4. Worker restarts, picks up same message again
  5. POST to XMI → 200 OK        ← XMI receives duplicate
```

**How idempotency is ensured (two layers):**

**Layer 1 — Habu side (delivery_log deduplication):**
```java
// Before POSTing, check if already successfully delivered
boolean alreadyDelivered = deliveryLogRepo.existsSuccess(registrationId, eventId);

if (alreadyDelivered) {
    sqsClient.deleteMessage(receiptHandle);  // ACK and skip
    return;
}
// proceed with POST
```

**Layer 2 — XMI side (event ID deduplication):**
```
Every POST carries header: X-Habu-Event-Id: evt-789-uuid

XMI stores received event IDs (Redis or DB, TTL 7 days):
  if redisClient.exists("received:" + eventId):
      return 200 OK  // already processed, acknowledge but skip
  
  redisClient.setex("received:" + eventId, 7*24*3600, "1")
  processEvent()
```

**Why both layers:**
- Habu-side dedup: prevents Habu from sending the same event twice (worker restart scenario)
- XMI-side dedup: protects XMI even if Habu's dedup fails for any reason
- Defence in depth — neither layer alone is fully reliable under all failure modes

**The contract we document for XMI integration:**
> "Habu delivers at-least-once. Every event carries X-Habu-Event-Id.
> Consumers must implement idempotent handlers using this ID."

## 7. DLQ Admin UI — Is It a New UI?

**Short answer: Yes, it is a new UI panel, but it does not need to be a standalone app.**

**Three options for where it lives:**

**Option A — Inside existing Activity Feed tab (MVP-friendly):**
```
Clean Room: Acme Corp x LiveRamp
[Overview]  [Questions]  [Data Connections]  [Activity]  [Webhooks ▼]

Webhooks tab:
  Registered callbacks:
    cb-456  XMI  QUESTION q-123  ✓ Healthy  Last: 10:32
    cb-457  XMI  DATA_CONNECTION dc-789  ✗ 3 in DLQ  [Replay All]

  DLQ Messages:
    evt-899  QUESTION "Revenue Analysis" — DELETED  Failed: 3x timeout  [Replay]
    evt-812  DATA_CONNECTION "CRM_Import" — type changed  Failed: 500  [Replay]
```
This is V2 scope. A new tab in the existing clean room UI.
No new service needed — reads from delivery_log table + DLQ.

**Option B — Ops/Admin page (internal only, faster to build):**
A Habu-internal admin page (not customer-facing) showing DLQ depth across all registrations.
Ops team uses it, not customers. Simpler auth requirements.

**Option C — CloudWatch Console only (V1 DLQ strategy):**
No UI at all for MVP. CloudWatch alarm pages on-call when DLQ depth > 0.
On-call uses AWS console to inspect and replay.
Zero UI build time. Acceptable for MVP.

**Recommendation:**
- V1/V2: CloudWatch alarm + ops uses AWS console for DLQ management
- V3: Add the Webhooks tab with delivery status + one-click replay to the clean room UI

## 9. Catchphrase Summary for TLM Presentation

| Term | One-line explanation |
|------|----------------------|
| **Fan-out** | One event, N independent consumers — new consumer = zero code change |
| **Circuit breaker** | Stops calling a broken endpoint automatically, recovers when it heals |
| **HMAC signature** | Cryptographic proof every POST is genuinely from Habu, payload untampered |
| **Dead Letter Queue** | Failed deliveries never silently dropped — ops can inspect and replay |
| **Delivery observability** | Every HTTP attempt logged — latency, status, failure reason, per registration |
| **At-least-once + idempotency** | SQS guarantees delivery; Event ID header lets receiver safely deduplicate |
