1.2 WHERE THE EVENT GOES: BETWEEN LINE 378 AND LINE 379
--------------------------------------------------------------------------------
Why exactly there, and not earlier:
  - NOT after :356 (InsertJobV2). The Snowflake block at :362-371 can still
    return an error, and the caller would be told the create failed while XMI
    was told it succeeded. Emitting after :371 makes the event always true.
  - NOT before :372. protoDataConnection does not exist yet.
  - AT :378/:379 everything is assembled and every failure path has already
    returned. This is the last line before success.

2.4 WHY `After` IS NOT jobModel — THE TRAP
--------------------------------------------------------------------------------
[VERIFIED] forebitt/models/data_import_job.go:76-85 —
    func NewImportJobFromProtoV2(p *dataconnections.DataConnection) DataImportJob {
        return DataImportJob{
            Name:               p.Name,
            Category:           p.Category,
            OrganizationID:     p.OrganizationID,
            ImportDataTypeID:   p.DatasetTypeID,
            ImportDataSourceID: p.DataSourceID,
            CredentialID:       p.CredentialID,
        }
    }

SIX FIELDS. No Status. No Stage. No CurrentTries, ErrorMessage, IsInternal, etc.

[VERIFIED] forebitt/db/job_v2.go:45 —
    tx.Model(&models.DataImportJob{}).Updates(*job)
GORM v1 converts the struct to a map of NON-ZERO fields; blanks are dropped.

So jobModel is a PATCH, not the after-state. If we diffed dbJob against jobModel
directly, every single update would emit garbage like:

    "status": { "from": "ACTIVE",           "to": "" }
    "stage":  { "from": "MAPPING_REQUIRED", "to": "" }

which is not just noise — it is WRONG, and XMI's stage-change consumer would act
on it.

THE FIX — build the after-state by overlaying the patch onto the before-image:

    after := *before                       // start from the true current row
    if patch.Name != ""               { after.Name = patch.Name }
    if patch.Category != ""           { after.Category = patch.Category }
    if patch.ImportDataTypeID != ""   { after.ImportDataTypeID = patch.ImportDataTypeID }
    if patch.ImportDataSourceID != "" { after.ImportDataSourceID = patch.ImportDataSourceID }
    if patch.CredentialID != ""       { after.CredentialID = patch.CredentialID }
    // OrganizationID deliberately not overlaid — :403 already proved it unchanged
    changed := diffJob(before, &after)     // emits only real differences

This mirrors GORM's own zero-value semantics deliberately and explicitly, in six
lines, rather than leaving it implicit. The alternative is a re-fetch after :432
(one more read, zero reasoning) — recorded as OPEN-2. My recommendation is the
overlay for M1 because the patch surface is exactly these six fields and they are
right here in the file; switch to re-fetch if that surface ever widens.

2.5 PARAMETER DIFF — BY BUSINESS KEY, NEVER BY ROW ID
--------------------------------------------------------------------------------
[VERIFIED] job_parameters.go:150 — inParamObj.ID = uuid.New().String() on every
save, after a condition-scoped DELETE of all existing rows (:81). Row identity
does not survive an edit.

    func diffParams(before, after []*models.OrganizationJobParameter)
                   map[string]FromTo {
        key := func(p *models.OrganizationJobParameter) string {
            return p.ImportDataSourceParameterID + "|" + p.Name   // STABLE
        }
        // build maps by key, then emit only entries whose Value differs,
        // plus added (from=null) and removed (to=null)
    }

Emit the diff keyed by parameter NAME so it reads naturally to a consumer, and
do NOT put the parameter row id in the payload at all — it is unstable by
construction and would mislead anyone who tried to use it as an identifier.

PART 3 — HOW UpdateDataConnectionV2 DIFFERS FROM UpdateDataConnection
================================================================================
These are two different generations of API sitting side by side, and they behave
completely differently. This matters for us because it decides WHERE we emit and
how we avoid emitting twice.

--------------------------------------------------------------------------------
3.4 THE NUMBER TO PUT IN FRONT OF ANIL
--------------------------------------------------------------------------------
Hank hook firings for ONE user action, "create a data connection with 3
parameters":

  VIA THE V2 API (CreateDataConnectionV2):
      1  AfterCreate  DataImportJob
      1  AfterDelete  OrganizationJobParameter   (phantom — matches 0 rows)
      3  AfterCreate  OrganizationJobParameter
      = 5 hook firings

  VIA THE V1 API (CreateDataConnection):
      pass 1:  1 AfterCreate job + 1 AfterDelete param (0 rows) + 3 AfterCreate param
      pass 2:  1 AfterUpdate job + 1 AfterDelete param (3 rows) + 3 AfterCreate param
      = 10 hook firings

  In the V1 case the same three logical parameters are created, deleted and
  created again — SIX parameter-create records carrying SIX DIFFERENT uuids
  (job_parameters.go:150) for THREE parameters, plus two delete records both
  carrying ObjectID "" (empty struct passed to Delete, job_parameters.go:81).
  And the job appears once as CREATE and once as UPDATE.

  A hook-based assembler receiving those ten records would have to conclude, from
  no field values, no parent references, no transaction id and no completeness
  marker, that this was ONE data connection created ONCE with THREE parameters.

  By contrast the service-layer approach emits exactly ONE event, from ONE line,
  in ONE place, in BOTH cases — because the handler knows what the user asked
  for, and the hook only knows what the tables did.

--------------------------------------------------------------------------------
3.5 CONSEQUENCE FOR US: THE DOUBLE-EMISSION RULE
--------------------------------------------------------------------------------
Because V1 delegates into the same inner RPCs, we must NOT put the emit inside
CreateImportJobV2 / UpdateImportJobV2 / UpdateImportJob — the V1 create would
then emit twice (once per pass at :1418 and :1425).

RULE: emit at the OUTERMOST handler the caller actually invoked, and suppress
nested emission.

  EMIT HERE:
    dataConnections_v2.go:378   CreateDataConnectionV2
    dataConnections_v2.go:453   UpdateDataConnectionV2
    job_service.go:1505         CreateDataConnection      (V1 wrapper)
    job_service.go:1698         UpdateDataConnection      (V1 wrapper)
    job_service.go:1932         DeleteImportJob           (beside the thin publish)

  DO NOT EMIT HERE (internal, called by the above):
    job_service.go:1293         CreateImportJobV2
    job_service.go:1624         UpdateImportJobV2
    job_service.go:1538         UpdateImportJob

  MECHANISM: a context flag set by the outer handler.

      ctx = observability.WithSuppressed(ctx)     // set before nested calls
      ...
      func (s *Server) emitDataConnectionEvent(ctx, change) {
          if observability.IsSuppressed(ctx) { return }
          ...
      }

  This is needed because CreateImportJobV2 and UpdateImportJobV2 are themselves
  public RPCs — [UNVERIFIED] whether external-api-server or the UI call them
  directly today. If they do, they need their own emit, guarded by the flag so
  the V1 wrapper path still produces exactly one event. CONFIRM THE CALLERS
  BEFORE IMPLEMENTING — this determines whether we instrument 5 sites or 8.

--------------------------------------------------------------------------------
3.6 WHICH API IS ACTUALLY LIVE?
--------------------------------------------------------------------------------
[UNVERIFIED] and it matters a great deal:
  - If the UI is fully on V2, we instrument 2 handlers plus delete and we are
    done, and the 10-hook V1 example is a historical argument rather than a live
    one.
  - If V1 is still serving traffic, we instrument both families, and the V1 path
    is where the double-emission rule earns its keep.
  - If V1 is dead, it is worth saying so out loud — it is ~130 lines of
    orchestration whose only remaining purpose would be backwards compatibility.
