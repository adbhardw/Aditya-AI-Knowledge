1. Finalize orinix language & architecture decision (Java, Strategy pattern)

Decided orinix (new cleanroom observability service) is Java/Spring Boot,
not Go, and not a Java+Go hybrid. Reasoning: SQS consumption and GCP
Pub/Sub publish are both already proven in production Java (pegleg's
AWSSQSConfiguration and BillingMessagePublisherHelper); neither exists in
Go anywhere in this codebase (hank has no SQS support). WIF is proven in
both languages so that didn't tip it. Full comparison (Java vs Go vs
Hybrid, every option scored against SQS/Pub-Sub/WIF/precedent) is written
up in orinix-why-and-how/2026-07-06d_q1_FINAL_java_vs_go_vs_hybrid.txt.
Status: Done.

2. Scaffold orinix repository (orinix-proto / orinix-backend / orinix-server)

Multi-module Maven/Spring Boot repo created at LiveRamp/orinix, mirroring
pegleg's own module split. orinix-proto holds the gRPC contract

3. Implement webhook delivery channel (HMAC-SHA256 signed)

WebhookDeliveryChannel implements the Strategy interface DeliveryChannel.
POSTs the CloudEvents payload to a registered callback_url, signs it with
HMAC-SHA256 using a per-registration signing_secret (symmetric, same
model as Stripe/GitHub webhooks), attaches X-Habu-Signature and
X-Habu-Event-Id headers.
Status: Done (implementation), open: end-to-end test against a real XMI
endpoint has not happened yet.

4. Implement GCP Pub/Sub delivery channel — resolve WIF vs static SA key

PubSubDeliveryChannel implements the same DeliveryChannel interface,
publishing via com.google.cloud.pubsub.v1.Publisher. Currently scaffolded
using Workload Identity Federation (OrinixPubSubCredentialsProvider, using
zabra-aws's GoogleIdentityFederationAwsToken). Open decision, not yet
made: WIF (more setup cost, no standing credential) vs a static GCP
service-account key (matches pegleg's proven billing-publisher pattern,
much lower setup cost for exactly one known consumer today). Full
tradeoff writeup: orinix-why-and-how/2026-07-07_q7_cursor_idempotency_hmac_dlq_wif.txt.
Status: Open — needs a decision before this channel can be considered final.

5. Idempotency design — producer-minted event ID, end-to-end propagation

The idempotency key is the CloudEvents envelope's own `id` (a UUID), minted
once by the producing service, reused across that producer's own publish
retries, and propagated unchanged through SNS -> SQS -> object_events
(unique constraint) -> X-Habu-Event-Id header (webhook) -> should also be
a Pub/Sub message attribute (not yet added to PubSubDeliveryChannel —
see action item below). XMI (and any consumer) must dedupe on this ID,
since delivery is at-least-once, never exactly-once.
Status: Mostly done. Remaining: attach event ID as a Pub/Sub message
attribute in PubSubDeliveryChannel so PUBSUB consumers can dedupe the same
way webhook consumers do.

6. DLQ handling + log-backed event replay

DLQ is a separate SQS queue per consumer (e.g. sqs-habu-dlq-xmi), wired
via SQS's native redrive policy (maxReceiveCount=5) — no custom
application code for the routing itself. Replay has two tiers: SQS's own
start-message-move-task action for recent failures (bounded by ~14-day
queue retention), and a new ReplayService (reads directly from
object_events, unbounded, reuses the same cursor query GetCleanroomEvents
already uses) for reprocessing/backfill cases a queue-bounded redrive
can't reach. CallbackDeliveryWorker refactored to expose a shared
deliverToRegistration() method so live delivery and replay never diverge.
Status: Done (code + design). Open: whether a delivery_log table is
wanted for Habu-side observability/dedup on top of this (currently
skipped for M1 — XMI-side dedup via event ID is the required correctness
layer regardless).

11. Decide migration tooling standard — Liquibase vs plain SQL

The original design doc assumed Liquibase (matches unhygienix/Go
convention — changelog.yaml), but neither pegleg nor cronos (the Java
services orinix's shape is modeled on) use Liquibase — both apply plain
versioned .sql files by hand. orinix's actual migrations
(001_create_object_events.sql, 002_create_callback_registrations.sql) are
plain SQL for now, matching the Java-fleet convention, but this was a
judgment call, not a confirmed platform standard.
Status: Open — flagged for Anil (Principal Architect) at LIDAC, not yet
answered.
