Q0. First, the doubt: why did you call it a "dual write" problem? We are fine
    with the current approach.
================================================================================
Fair challenge, and the decision to stay as-is is fine — I am recording the
term's meaning, not re-arguing the choice.

"Dual write" is the standard name for: ONE logical operation writes to TWO
independent systems with no shared transaction, so either can succeed while the
other fails, and nothing reconciles them afterwards.

Here the two systems are Postgres and SNS:

  [VERIFIED] forebitt/db/job_v2.go:19-31 — InsertJobV2 opens a transaction,
             writes, and COMMITS.
  [VERIFIED] the publish happens AFTER that commit returns, in the handler, and
             the error is logged and swallowed (job_service.go:1602-1605):
                 eventErr := events.PublishEvent(...)
                 if eventErr != nil { hlog...Errorln(...) }   // RPC still returns success

So the failure mode is: DB row committed, SNS publish failed, event never
existed, and no retry or reconciliation exists. That is at-most-once.

Two things worth being precise about, both of which support "we are fine":

  1. IT IS LOSS-ONLY, NOT PHANTOM. Because the publish is strictly AFTER the
     commit, we can never emit an event for a row that does not exist. We can
     only fail to emit one for a row that does. Loss is much easier to live with
     than phantom events, and it is recoverable by other means (a backfill from
     the source table).

  2. THE ONE PLACE A PHANTOM COULD APPEAR IS PLACEMENT, NOT TRANSPORT.
     [VERIFIED] dataConnections_v2.go:364-371 — the Snowflake setup block can
     return an error AFTER InsertJobV2 has already committed. If we emit the
     event before that block, we would announce a data connection the caller was
     told failed. Fix is free: emit at the END of the handler. Covered in Q2.

DECISION RECORDED: staying with fire-and-forget publish for M1. Consequence to
state honestly in the XMI contract: delivery is at-least-once ONCE THE EVENT IS
PUBLISHED, but publication itself is best-effort. UNIQUE(idempotency_key)
protects against duplicates, not against loss. If we later need to close it, the
answer is a transactional outbox, and the code changes here do not block that —
the publish call site is the same place an outbox write would go.

Q2. For UPDATE — what do we need so that `from` and `to` are populated properly?
================================================================================
This is the only place with real work. Three concrete gaps, all solvable.

--------------------------------------------------------------------------------
GAP 1 — THE OLD PARAMETERS ARE NEVER FETCHED
--------------------------------------------------------------------------------
[VERIFIED] UpdateDataConnectionV2 (dataConnections_v2.go:383-455):
    dbJob, notFound := db.FetchJobByID(s.DB, in.DataConnection.ID)   // :393
        ^-- the JOB's before-state IS available
    dbParameters := make([...], len(in.DataConnection.JobParameters)) // :420
        ^-- built ENTIRELY from the request — these are the NEW values
    err = db.UpdateJobV2(ctx, s.DB, &jobModel, dbParameters)          // :432

Nowhere are the EXISTING parameter rows read. And UpdateJobV2 ->
SetOrganizationJobParametersInTransaction -> ClearOrganizationJobParameters only
fetches parameter IDs (job_parameters.go:72), never the rows' values.

FIX: one added read before the write. The function already exists —
    [VERIFIED] forebitt/db/job_parameters.go:20
      func FetchOrganizationJobParameters(db *gorm.DB, queryKey *OrganizationJobParameterKey)
                ([]*models.OrganizationJobParameter, error)

    // add before line :432
    beforeParams, err := db.FetchOrganizationJobParameters(s.DB,
        &db.OrganizationJobParameterKey{
            OrganizationID:  in.DataConnection.OrganizationID,
            DataImportJobID: in.DataConnection.ID,
        })

THIS IS THE ONLY NEW QUERY IN THE ENTIRE DESIGN. One indexed read, on an update
path that already performs several.

--------------------------------------------------------------------------------
GAP 2 — jobModel IS A PATCH, NOT THE AFTER-STATE
--------------------------------------------------------------------------------
[VERIFIED] forebitt/models/data_import_job.go:76-85 — NewImportJobFromProtoV2
maps SIX fields only:
    Name, Category, OrganizationID, ImportDataTypeID, ImportDataSourceID, CredentialID

It does NOT map Status or Stage. And [VERIFIED] UpdateJobV2 (job_v2.go:45) uses
    tx.Model(&models.DataImportJob{}).Updates(*job)
which in GORM v1 converts the struct to a map of NON-ZERO fields — blank values
are dropped entirely.

So the row after the update = dbJob, overlaid with the non-zero subset of those
six fields. If we naively diff dbJob against jobModel we would emit false
changes like status: {from:"ACTIVE", to:""} for every single update.

FIX — build the after-state explicitly rather than assuming jobModel is it:

    after := dbJob                       // start from the true current row
    applyNonZero(&after, jobModel)       // overlay only the fields this
                                         // endpoint can actually change
    changed := BuildChangedFields(dbJob, after)   // emit only real differences

ALTERNATIVE, for guaranteed truth: re-fetch the row after UpdateJobV2 returns and
diff dbJob against the re-fetched row. Costs one more read but removes all
reasoning about GORM's zero-value semantics from our code.
RECOMMENDATION: overlay for M1 (no extra read, and the six-field surface is small
and explicit); re-fetch if we later extend to endpoints with a wider patch
surface. Worth Anil's opinion — this is a correctness-vs-cost call, not a
preference.

--------------------------------------------------------------------------------
GAP 3 — PARAMETERS MUST BE DIFFED BY BUSINESS KEY, NOT ROW ID
--------------------------------------------------------------------------------
[VERIFIED] job_parameters.go:150 — inParamObj.ID = uuid.New().String() on EVERY
save. Combined with the condition-scoped DELETE at :81, editing one parameter
destroys and recreates every parameter row with fresh primary keys.

So a diff keyed on the row's primary key reports "all parameters replaced" on
every update, forever.

FIX: key the diff on (ImportDataSourceParameterID, Name) — the stable business
identity — and emit:

    "parameters": {
      "from": { "DataLocation": "s3://adidas-emea-cleanroom/crm/customers/" },
      "to":   { "DataLocation": "s3://adidas-emea-cleanroom/crm/customers_v2/" }
    }

i.e. only the parameters that actually changed value, keyed by parameter name.
Also implies: we should NOT expose the parameter row id in the event at all, as
it is unstable by construction.

--------------------------------------------------------------------------------
RESULT FOR UPDATE
--------------------------------------------------------------------------------
    "type": "com.habu.cleanroom.data_connection.updated",
    "changeType": "UPDATED",
    "changedFields": {
      "parameters": {
        "from": { "DataLocation":   "s3://adidas-emea-cleanroom/crm/customers/",
                  "FieldDelimiter": "," },
        "to":   { "DataLocation":   "s3://adidas-emea-cleanroom/crm/customers_v2/",
                  "FieldDelimiter": "|" }
      }
    }

NET NEW WORK FOR UPDATE: one added read, one overlay helper, one diff function,
one publish block.

Q3. For DELETE — what is needed?
================================================================================
[VERIFIED] DeleteImportJob (job_service.go:1846) already has the full
before-state: dbJob fetched at :1858, still in scope at the existing publish at
:1932.

  - `to` is null for every field (changeType = DELETED).
  - `from` = dbJob. If we want parameters in `from`, add the same
    FetchOrganizationJobParameters call from Gap 1. Recommend yes — a delete
    event that cannot tell you what the connection was configured as is much
    less useful for the "what did we lose" question.
  - Emission point: beside the existing thin publish at :1932, not replacing it
    (pegleg/janus depend on the thin one).
  - Note it is a SOFT delete (db.SoftDeleteJob -> job.go:185), so DELETED here
    means "removed from the user's view", not "row gone". Worth stating in the
    contract so XMI does not assume the data is unrecoverable.

NET NEW WORK FOR DELETE: one optional read, one publish block.

Q4. Full work breakdown — everything, not just the handler code
================================================================================

A. CONTRACT / PAYLOAD  (new code, forebitt)
  A1. New package forebitt/services/observability/ holding the CloudEvents
      envelope struct + the DATA_CONNECTION data struct.
  A2. BuildChangedFields(before, after) — reflective or explicit field diff,
      returning map[string]{from,to}. Explicit is better here: it doubles as the
      field allow-list, so nothing new leaks into the event just because someone
      added a column.
  A3. diffParameters(before, after []*OrganizationJobParameter) keyed on

Q5. Why can Hank hooks not do this? Spell out the "5-6 hook combination" problem.
================================================================================
For Anil, the cleanest way to put it: describe the ASSEMBLER you would have to
build, and let the list speak.

One CreateDataConnectionV2 with 3 parameters produces FIVE hook firings
  [VERIFIED trace: dataConnections_v2.go:356 -> job_v2.go:13 -> job_parameters.go:109]

  1  INSERT data_import_jobs                          -> AfterCreate
  1  DELETE organization_job_parameters (matches ZERO -> AfterDelete  (phantom)
       rows on a create; condition-scoped, job_parameters.go:81)
  3  INSERT organization_job_parameters               -> AfterCreate x3

To turn those five back into the ONE event from Q1, something must:

  1. CORRELATE them. Only key available is RequestID. Works only if it is
     populated on every path [UNVERIFIED], and one request is not always one
     business event — CreateImportJobV2 (job_service.go:1293) performs a
     create-or-update PLUS a parameter replacement under a single request id.

  2. IDENTIFY THE AGGREGATE ROOT. Records 1 and 3-5 are structurally identical.
     Nothing in the record says DataImportJob is the root and
     OrganizationJobParameter is a child — that mapping exists only in the proto
     layer (models.NewImportJobFromProtoV2). The assembler needs a hand-
     maintained table->aggregate map living outside the producer that owns it.

  3. KNOW WHEN IT IS DONE. This is the one with no good answer. There is no
     count, no transaction id, no end-of-transaction marker in the record. The
     assembler cannot distinguish "3 parameters, all arrived" from "5
     parameters, 2 still in flight". The only implementable answer is a timer
     plus a heuristic — i.e. every event is delayed by the timeout, and a slow
     message silently produces a WRONG event rather than a late one.

  4. DISCARD THE PHANTOM DELETE (record 2), which is an artifact of the
     delete-then-reinsert implementation and means nothing to a consumer.

  5. RECONSTRUCT THE VALUES. Impossible today — [VERIFIED] hank/db/audit.go's
     AuditLog carries no field values at all, only
     ObjectID/ObjectName/ObjectType/Action/actor/Method/OrgID/RequestID.

  6. HANDLE THE MISSING IDENTITY. [VERIFIED] SoftDeleteJob (job.go:185) passes
     an empty struct with the id in the WHERE clause, so the delete record has
     ObjectID "". The assembler cannot even tell which connection was deleted.

  7. TOLERATE OUT-OF-ORDER ARRIVAL, since neither logs nor SNS Standard preserve
     order across records.

  8. BE MAINTAINED PER OBJECT TYPE, forever, in orinix — every new aggregate
     needs its own root map and completeness rule.

And even if all eight were solved, item 5 requires changing Hank's shared hook
anyway (~91 models, fleet-wide extra SELECT per update, plus a redaction policy
because primage.Credential.Value embeds hdb.Audit). At which point we have paid
the per-path cost of the service-layer approach AND built the assembler.

  THE ONE-LINER FOR ANIL:
    The hook fires per ROW. The contract is per RESOURCE. The mapping between
    them — which rows form one business action, which one is the root, and when
    the set is complete — exists only in the service layer. Emitting there uses
    that knowledge; emitting from the hook throws it away and asks orinix to
    guess it back, with a timer.

OPEN ITEMS NEEDING A DECISION
================================================================================
OPEN-1  CLEANROOM SCOPING. The approved envelope uses
        "source":"urn:habu:cleanroom:<cleanroom-id>" and object_events is
        queried by cleanroom_id, but DataImportJob carries OrganizationID and no
        CleanroomID [VERIFIED forebitt/models/data_import_job.go:20]. A data
        connection is org-scoped and may serve several cleanrooms. Options:
        (a) org-scoped source urn:habu:org:<id> with cleanroom_id null,
        (b) fan out one event per attached cleanroom,
        (c) emit once, let orinix expand at read time.
        This determines the primary query key. NEEDS A DECISION.

OPEN-2  AFTER-STATE: overlay vs re-fetch (Gap 2). Correctness-vs-one-read.

OPEN-3  NO-OP UPDATES. If a caller PUTs an identical payload, changedFields is
        empty. Emit nothing, or emit an event with an empty diff? Recommend emit
        nothing — but XMI may want the heartbeat.

OPEN-4  TWO CREATE PATHS. CreateDataConnectionV2 vs CreateImportJobV2
        (job_service.go:1293, a create-or-update orchestrator where the draft
        flow makes a user "create" arrive as an UPDATE). Are both live in prod?
        If so, instrument both without double-emitting when one calls the other.

OPEN-5  WHERE THE PAYLOAD TYPE LIVES. Fine in forebitt for one producer. When
        unhygienix/picanmix start producing, do we share a Go module, or treat
        the JSON schema as the contract and let each service own its struct?
        Recommend the latter — sharing a Go type would recreate exactly the
        coupling we are avoiding by not widening hevent.EventStruct.
