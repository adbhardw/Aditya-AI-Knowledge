  │                          pegleg-backend's role as the "library" module

  │   │                      object_events
  │   ├── delivery/          DeliveryChannel interface + WebhookDeliveryChannel
  │   │                      + PubSubDeliveryChannel (see pattern below)
  │   ├── registration/      CallbackRegistrationService — validates and
  │   │                      persists callback_registrations rows
  │   └── db/                JPA entities + migrations
  └── orinix-server/         Spring Boot app — mirrors pegleg-server: wires
                             the gRPC server, the SQS listener config, the
                             REST controller for POST /v1/cleanrooms/{id}/callbacks,
                             and the CallbackDeliveryWorker as a scheduled/
                             triggered job

THE DESIGN PATTERN FOR EXTENSIBILITY: STRATEGY, RESOLVED BY SPRING'S
QUALIFIER MAP — not a new idea, just naming what we already sketched

You asked for the best pattern so this is extensible for future delivery
mechanisms (and future event types). DeliveryChannel, as already designed
in the working-principle doc, IS the Strategy pattern: one interface,
interchangeable implementations, selected at runtime. What's worth adding
now is HOW it gets selected, because that choice is either clean or a pile
of if/else:

  public interface DeliveryChannel {
      String deliveryType();                      // "WEBHOOK", "PUBSUB", ...
      DeliveryResult deliver(CallbackRegistration reg, ObjectEvent event);
  }

  @Component("WEBHOOK")
  public class WebhookDeliveryChannel implements DeliveryChannel { ... }

  @Component("PUBSUB")
  public class PubSubDeliveryChannel implements DeliveryChannel { ... }

  // Spring auto-collects every DeliveryChannel bean into a Map keyed by
  // its @Component name — no factory class to hand-maintain, no switch
  // statement to extend every time a new channel shows up.
  @Service
  public class CallbackDeliveryWorker {
      private final Map<String, DeliveryChannel> channelsByType;   // injected
      void deliver(CallbackRegistration reg, ObjectEvent event) {
          channelsByType.get(reg.getDeliveryType()).deliver(reg, event);
      }
  }

Adding a third mechanism later (say, Azure Service Bus for a future MSFT
consumer) means writing one new @Component class and nothing else —
CallbackDeliveryWorker, the registration API, and the ingest path are all
already closed to that change.

Why this is the "best" pattern here rather than something fancier
(event bus, plugin loader, etc.) — GENERAL-PURPOSE MODULES (ch. 5): the
book's warning is to build the socket wrench, not fifty single-size
wrenches, but also not to over-generalize past what the problem needs.
Strategy + Spring's own DI container is exactly general enough for
"N delivery mechanisms, chosen per row" — reaching for a heavier plugin
architecture (dynamic classloading, config-driven registration) would be
solving a problem we don't have yet, which is its own form of complexity
Ousterhout warns about just as much as under-designing does.

One more principle this satisfies — PULL COMPLEXITY DOWNWARD (ch. 7):
CallbackDeliveryWorker is the only thing that knows delivery is
dispatched by a string key into a map. Nothing above it (ingest, the
registration endpoint) needs to know that detail exists.

    commit) relies on SQS's own visibility-timeout + redrive-policy (maxReceiveCount,
    DLQ on exhaustion) to track retry attempts — no hand-rolled attempts-counter
    table in Postgres. This matches the approved Confluence doc's stated retry
    policy ("5 attempts, exponential backoff, jitter, DLQ on exhaustion" per
    per-consumer queue), but it was a judgment call made while scaffolding, not
    something explicitly confirmed with you beforehand. Does this match what you
    had in mind, or did you picture the worker tracking delivery state in Postgres
    itself (e.g. a delivery_attempts column/table) instead of leaning on SQS's
    native redrive behavior? Not blocking the first commit, but worth confirming
    before this becomes harder to change.
