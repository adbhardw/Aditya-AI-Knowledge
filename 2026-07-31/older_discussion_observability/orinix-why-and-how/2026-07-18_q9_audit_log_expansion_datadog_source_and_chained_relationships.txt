Q9: Josh's Datadog audit log shows a "Method" that was invoked (e.g.
CreateQuestionRun). orinix's design shows what RESOURCE was impacted,
not the method. Is this a real conflict?

A: No — they're two different layers, and both can be kept without
picking one over the other.

Stripe, GitHub, and Salesforce all log resource + verb as the primary
audit field (charge.succeeded, repo.create), not an RPC/method name.
That's exactly orinix's existing event_type pattern:
com.habu.cleanroom.<object_type>.<action>. The "Method" Josh is
pointing at is very likely a generic interceptor logging the raw
gRPC route for every call it wraps — cheap to instrument exhaustively
across 80+ entity types because it doesn't need to know what each
call means, but it pushes "figure out what CreateQuestionRun means to
a customer" onto every downstream reader.

Fix: object_events.context_fields (JSONB, already exists, already
GIN-indexed) is exactly where "the method that was called" belongs as
ADDITIONAL metadata, not a replacement for object_type/change_type.
Adding e.g. "invokedMethod": "CreateCleanRoomQuestionRunStatistics" to
context_fields costs zero schema migration and satisfies both views
at once.

Q10: Right now object_events only captures CREATE/UPDATE. Can we save
READ events too? And can we use the cleanroom_id from request context
(the way Josh described using it for his write/update audit) to
populate these rows?

A: Read events are real, new instrumentation — not a config flag.

Confirmed in the 2026-07-08 diff doc: there is no emit point today on
any read/view path in pegleg, unhygienix, or picanmix. This is the
same gap Jon separately flagged (Q2 epic — "who viewed this data") and
it remains open regardless of what Josh's design covers.

Two things worth being explicit about before committing to it:

  1. Volume asymmetry — every GET vastly outnumbers every mutation.
     The current GIN index and the 90-day partial index on event_time
     are sized for a mutation-rate table, not a read-rate table.
     Adding reads without re-sizing that plan risks the same table
     doing two very different jobs badly.

  2. cleanroom_id context for reads is actually EASIER than Josh's
     problem, not harder. His Entity Enrichment Registry exists
     because ~70K/day of his events come from entities that don't
     carry cleanRoomId directly, needing chained ByID lookups. Read
     paths are almost always already scoped by an explicit
     cleanroomId path/query param — you need it to run the query in
     the first place — so there's no enrichment-registry equivalent
     needed for reads. Worth saying this directly to Josh: read-
     auditing does not inherit his hardest problem.

Q11: Is it possible to save all of this — write audit, read audit,
Josh's 80+ entity types — in the SAME object_events table, or do we
need something more?

A: Schema-wise, one table is right. Retention-wise, it isn't — yet.

Stripe, GitHub, and Salesforce all converge on one polymorphic shape
at the storage layer (actor + resource_type + resource_id + action +
metadata). object_events already has this: org_id, cleanroom_id,
object_type, object_id, event_type (the action), performed_by (the
actor), context_fields (JSONB, unstructured extra). No new columns
needed to hold more entity types or more action kinds.

What none of those companies collapse is RETENTION. Salesforce's
standard Setup Audit Trail is 6 months; Field Audit Trail (compliance-
grade) is a separate, explicitly longer-retention product tier.
GitHub's enterprise audit log is a differently-retained materialization
over the same event stream, not the same physical table serving both
an activity feed and a legal-hold audit trail.

The concrete blocker: object_events' current DDL runs a nightly hard
delete — "DELETE FROM object_events WHERE event_time < NOW() -
INTERVAL '90 days'" (2026-06-01/cloudevents_real_payload_examples_
2026-06-01.md, line ~561). That's fine for "notify XMI something
changed." It is not fine for "prove to a customer's compliance team
what happened in their cleanroom 14 months ago" — the actual point of
an audit log. This is the real architectural decision, more load-
bearing than whether the columns fit: does audit-grade data get a
separate longer-retention table/partition fed from the same event, or
does object_events' retention change wholesale (with the cost/volume
consequences of also carrying reads)? Worth sketching both before
picking one (Design It Twice — see Ousterhout tie-in below).

Q13: Chained/cascading relationships — if a Dataset changes, does that
mean the underlying Data Connection changed too (or vice versa)? If a
credential is rotated, does that mean both a credential event AND a
data_connection event should publish?

A: General principle: publish one event per row that actually
mutated, not one event per perceived business relationship. Don't
fabricate an event on object B just because object A (which is
related to B) changed.

Stripe doesn't fire customer.updated when a related subscription
changes, and vice versa — each object gets its own event, fired only
when that object's own state was actually written. Two cases to tell
apart here:

  1. REAL cascading write — the "related" row is actually re-
     persisted as a side effect (e.g. a DataConnection schema push
     that causes a Dataset's schema_snapshot to be rewritten too).
     This is not double-counting or a design problem — it's two real
     mutations, so two real events, exactly matching the pattern
     already used for DATA_CONNECTION.schema_changed in the existing
     examples (2026-06-01/cloudevents_real_payload_examples...
     Scenario 2). Nothing new needed here beyond instrumenting both
     write paths, same as any other publisher.

  2. NO second write, but a real "this affects a downstream resource"
     relationship the consumer still needs to know about (e.g.
     rotating a Credential doesn't touch any DataConnection row, but
     XMI's workflow cares that a DataConnection depending on that
     credential might now need re-validation). Don't synthesize a
     fake data_connection.updated with an empty/fabricated diff here
     — changedFields must reflect a real diff on that specific row,
     or every consumer's "trust changedFields" assumption breaks.
     Instead: publish the one real event (credential.updated) and put
     the reference to what it affects in context_fields —
     e.g. "affectedDataConnectionIds": [...] — the exact same pattern
     already used for context.questionId on EXPORT_JOB events, where
     Question didn't change but the export job's context still names
     it.

Q14: Does an audit log line get emitted because of something on the
DATABASE TABLE (a column, a trigger), or because of a METHOD that
gets called somewhere? Walk through CreateDataConnection concretely,
simply.

A: It's a method, purely. Nothing about the database table matters —
no column, no DB trigger, no config anywhere in Postgres. It's a
property of the Go struct definition, checked automatically by GORM
every time you call Create/Update/Delete. Here's the mechanism, then
the concrete trace.

  THE MECHANISM, simply:

  GORM (the ORM library) has a built-in habit: whenever you call
  db.Create(&thing), right after it inserts the row, it asks "does
  `thing` happen to have a method called AfterCreate?" If yes, GORM
  calls it automatically. This is just Go: if a struct EMBEDS another
  struct that has a method, the outer struct gets that method for
  free, as if it wrote it itself.

  hank/db/audit.go defines a small struct called `Audit` with methods
  AfterCreate, AfterUpdate, AfterDelete on it. Any model that embeds
  `hdb.Audit` — like `type DataImportJob struct { UUID; hdb.Audit;
  ... }` — automatically GETS those three methods. GORM doesn't know
  or care that they came from Hank; it just sees "this struct has an
  AfterCreate method" and calls it after every insert. That's the
  whole trick. A model that does NOT embed hdb.Audit simply doesn't
  have the method, GORM's check finds nothing, and no audit line is
  ever produced for it — silently, no error.

  (Side note on BeforeCreateHook/BeforeUpdateHook specifically — those
  two are NOT GORM's standard method names, so they need the extra
  step in hank/db/service.go's applyEmbeddedHooks(), which manually
  registers a callback that looks for a method with exactly that name
  and calls it if found. AfterCreate/AfterUpdate/AfterDelete don't
  need this extra step — GORM already looks for those three by
  default on every model, no registration required.)

  THE CONCRETE TRACE — CreateDataConnection, actually followed line by
  line, not assumed:

    1. forebitt/api/server/job_service.go:1396
       CreateDataConnection(ctx, in) — the RPC handler.

    2. It calls CreateImportJobV2(...) (job_service.go:1293) twice —
       once with IsDraft=true to create the row, once with
       IsDraft=false to finalize it. (This is also why forebitt's own
       CreateDataConnection produces at least two separate audit log
       lines for one user action — one CREATE, one UPDATE — worth
       knowing if Jon ever counts audit lines and expects 1:1 with
       user actions.)

    3. The draft branch calls CreateImportJob(...) (job_service.go:
       1082), which calls InsertJob(...) (forebitt/db/job.go:146),
       which calls InsertJobInTransaction(tx, job) (job.go:162).

    4. Line 163, the actual moment: `err := tx.Create(&job).Error` —
       `job` is a `*models.DataImportJob`, which embeds `hdb.Audit`.

    5. GORM runs the INSERT, then — automatically, no extra code
       anywhere in forebitt — checks "does *models.DataImportJob have
       an AfterCreate method?" Yes, inherited from hdb.Audit. GORM
       calls job.AfterCreate(scope).

    6. That method (hank/db/audit.go) reads the JWT claims off the
       request context (actor: user ID/email) plus whatever log
       fields the service's own auth interceptor already attached
       (method: the gRPC route, organizationID: from the JWT) —
       builds an AuditLog struct, and logs it as one JSON line:
       "Audit Log: {...}".

    7. Datadog's Agent, tailing that container's stdout, ships the
       line to Datadog. That's the log Josh screenshotted.

  Nothing in steps 4-7 required forebitt's engineers to write any
  audit-specific code for DataImportJob — embedding hdb.Audit in the
  struct definition was the entire opt-in. That's also exactly why
  Josh's design covers 80+ entity types so easily: it's one line
  (embed hdb.Audit) per model, not per-mutation-path instrumentation.

Q15: [Aditya asked to check primage specifically] For the credential
rotation question left open in Q13 — does rotating a credential in
primage create a brand-new row, or update the existing one in place?
Does this change whether a DataConnection write is implied?

A: Checked primage/db/credentials.go directly. The answer is more
layered than "one row" — there are two different models involved, and
they behave differently on rotation.

  There are TWO levels in primage, not one:
    OrganizationCredential — the stable "bundle" (one per org +
      credential source, e.g. "Acme Corp's Snowflake credentials").
      This is almost certainly what DataImportJob.CredentialID
      actually points to (grounded in DataImportJob's own
      NewImportJobFromProtoV2 pulling CredentialID straight off the
      DataConnection proto, at the org/source-account level, not an
      individual secret field).
    Credential — individual field-level values underneath a bundle
      (e.g. one row for "password", one for "access key"). Both
      models embed hdb.Audit independently.

  UpdateOrganizationCredential (primage/db/credentials.go:398), the
  actual rotation path:
    - `tx.Model(oc).Updates(*oc)` on the OrganizationCredential — an
      IN-PLACE update, SAME ID preserved. This alone fires hdb.Audit's
      AfterUpdate hook on OrganizationCredential (it embeds hdb.Audit
      too — confirmed in primage/models/models.go).
    - Then: `tx.Scopes(...).Delete(&models.Credential{})` — DELETES
      every individual Credential row under that bundle — followed by
      CreateCredential(...) in a loop — CREATES brand-new Credential
      rows with brand-new IDs for the new values. So at the
      individual-field level, rotation really is delete-then-recreate,
      not an update.
    - Net effect: one rotation action can produce MANY audit log
      lines — one AfterUpdate (OrganizationCredential) + N AfterDelete
      + N AfterCreate (one pair per individual credential field) —
      not the one-line-per-action a human would picture.

  What this means for Q13's open question: since DataImportJob.
  CredentialID most likely points at the STABLE OrganizationCredential
  ID (which is updated in place, ID never changes), rotation does NOT
  force a write to DataImportJob — Case 2 from Q13 (no real second
  write, use context_fields to reference the affected DataConnection)
  is the right model, not Case 1. NOT independently verified: that
  DataImportJob.CredentialID literally equals OrganizationCredential.ID
  and not some individual Credential.ID — inferred from how the proto
  mapping and the RPC naming (GetOrCreateOrganizationCredential,
  CreateOrganizationCredential) are structured, not confirmed by
  reading a line that assigns one directly to the other. Worth a final
  grep on that specific assignment before stating it as fact to Josh.

  GOOD NEWS while checking that: the reverse lookup this whole
  question needs already exists. forebitt/api/server/job_service.go:
  436, GetDataConnectionCountByCredential(ctx, in) — takes a
  CredentialID, calls db.FetchDataConnectionCountByCredentionID
  (job.go:264), returns how many DataConnections reference it. That's
  exactly the query an "affectedDataConnectionIds" context field on a
  credential.updated event would need to run. So the cross-service
  reverse-lookup flagged as "real integration work" above is only
  partially new work — the read path forebitt would need already
  exists as a callable RPC; what's missing is wiring it into whatever
  publishes the credential event, not building the lookup from
  scratch.

Q16: Does UPDATE or DELETE call AfterUpdate/AfterDelete the same way
CREATE calls AfterCreate? Simple example against a real struct
(unhygienix/models/measurement.go:57, MeasurementDataset).

A: Yes, exactly parallel — one method per verb, GORM picks the one
matching whichever call you actually made.

  type MeasurementDataset struct {
      UUID
      hdb.Audit          // <- embedding, no field name, just the type
      MeasurementPlanReportID string
      DatasetID               string
      ...
  }

  Because hdb.Audit is embedded (not named as a field), Go gives
  MeasurementDataset every method Audit defines, for free, as if
  MeasurementDataset had written them itself: AfterCreate, AfterUpdate,
  AfterDelete, BeforeUpdateHook. GORM doesn't know or care they came
  from Audit — after any DB call, it just asks "does this struct have
  a method with this exact name?" and calls it if so.

    db.Create(&measurementDataset)              -> checks AfterCreate -> Action: "CREATE"
    db.Save(&measurementDataset) / .Update(...)  -> checks AfterUpdate -> Action: "UPDATE"
    db.Delete(&measurementDataset)               -> checks AfterDelete -> Action: "DELETE"

  Same struct, same embedded Audit, only the Action field in the
  logged line changes, based on which of the three GORM calls actually
  ran — nothing else differs between a create-triggered log line and
  an update-triggered one.

  One real asymmetry worth flagging: hdb.Audit has BeforeUpdateHook
  but no equivalent BeforeDeleteHook — only AfterDelete exists for
  deletes. So delete audit lines only ever see state from after GORM
  has already done the delete-scope work; there's no "before" hook to
  capture pre-delete detail the way BeforeUpdateHook can for updates.

Q19: For the cold tier (S3/GCS archive) — how would someone actually
access/query it "quickly" when they need older audit history? Isn't
object storage slow to search?

A: Two real options, with a real tradeoff between them — worth naming
both in the review rather than promising one speed for everything.

  OPTION A — partitioned query engine directly over the archive
  (Athena over S3 Parquet, or BigQuery external tables over GCS).
  If the archive is partitioned to match how people actually ask for
  it — by cleanroom_id, then by date — a query like "show CR-1's
  activity from March" only scans that partition's files, not the
  whole archive. This runs in low single-digit seconds for a
  well-partitioned query, not real-time-millisecond like Postgres, but
  genuinely interactive — someone can click into an "older history"
  tab and get an answer while they wait, not file a ticket and come
  back tomorrow. This is the right default for "show it in a UI."

  OPTION B — Datadog-style rehydration: temporarily reload a whole
  time range back into a hot searchable index, investigate there, let
  it expire back out. This is built for occasional deep investigation
  (a compliance audit, an incident review), not everyday browsing —
  Datadog's own default rehydrated-log retention is 15 days, and the
  reload itself takes real time, not instant. Wrong tool for "customer
  clicks a tab and expects an answer in 2 seconds."

  Recommendation: Option A (partitioned Athena/BigQuery-style engine)
  for anything user-facing, i.e. the "audit history" tab in a UI.
  Option B (rehydration) only if Habu ever needs Datadog-specific
  investigation tooling on top, which is a separate, lower-priority
  need. The real tradeoff to be upfront about in the review: object-
  storage query engines are NOT as fast as a live Postgres index no
  matter how well partitioned — if a genuinely instant/low-latency
  requirement shows up for old data, that's an argument for extending
  the HOT tier's retention instead of relying on cold storage, and
  should be raised as a real cost-vs-latency tradeoff, not assumed
  away.

OUSTERHOUT TIE-IN

  DEEP VS. SHALLOW MODULES (ch. 4) — Hank's generic per-RPC interceptor
  (Q9, Q12) is shallow by design: trivial to apply everywhere, but it
  hands the reader the raw method name instead of a resolved meaning.
  orinix's curated object_type/action pair is deeper: more thought at
  publish time, nothing left for the consumer to reverse-engineer.

  INFORMATION HIDING (ch. 4) — in Q13 case 2, a consumer reacting to
  "my data connection may be affected" shouldn't need to know HOW
  credentials relate to data connections internally. Putting
  affectedDataConnectionIds in context_fields hides that relationship
  behind the one event that actually changed.

  PULL COMPLEXITY DOWNWARD (ch. 8) — same case: the publisher already
  knows the credential-to-DC relationship at write time and resolves
  it once. Not doing this pushes "go figure out which DC this
  credential affects" onto every consumer, repeatedly.

  DEFINE ERRORS OUT OF EXISTENCE (ch. 9) — refusing to fabricate a
  second event with an empty diff (Q13) isn't a style preference, it
  eliminates a whole category of "trusted changedFields turned out to
  be lying" consumer bugs before they can exist.

  DESIGN IT TWICE (ch. 4) — the retention question in Q11 (same table,
  same TTL vs. a separate longer-retention audit partition) is a
  genuine two-options-worth-sketching decision, not something to
  settle in the same breath as "does the column exist."

  CHESTERTON'S FENCE, APPLIED PROSPECTIVELY — the Dataset/DataConnection/
  Credential relationship in Q13 and the RPC-layer-vs-ORM-layer question
  in Q12 were both explicitly flagged rather than assumed when first
  raised, and both got resolved the same day by reading the actual
  source (see the CORRECTED blocks in Q12 and Q13) instead of staying
  open guesses. One genuine remainder: whether credential rotation in
  primage creates a new Credential row or mutates Value in place wasn't
  traced to its actual call site — still flagged as open in Q13, not
  assumed either way. The same verify-before-generalizing discipline
  also caught the stage-vs-production mixup in Q12 (the screenshot was
  assumed to be a production row and wasn't — env:stage in the full
  payload's tags caught it), and echoes the cronos FLOW_RUN mistake
  earlier in this project — applied here after the fact instead of
  before, but applied.
