OUSTERHOUT PRINCIPLES MAPPED TO THIS DECISION (every one used, named explicitly)

  DESIGN IT TWICE (ch. 10)
    This whole table. Three real sketches, not one obvious pick rubber-stamped.

  DEEP MODULES vs SHALLOW MODULES (ch. 3)
    A deep module needs real, hidden complexity behind a simple interface.
    In Java, that hidden complexity (SQS handling, Pub/Sub+WIF publish) is
    already built and hardened. In Go, choosing it means the "depth" is
    hollow on day one — it has to be manufactured from scratch. In Hybrid,
    the cross-language boundary is a complex interface hiding NOTHING new
    (both sides are already inside Habu's trust boundary) — the textbook
    shallow-module trap.

  INFORMATION HIDING (ch. 4)
    Whichever language wins, delivery_type + delivery_config hides "how do
    we push to this consumer" from the ingest path and registration API.
    Independent of the language call, but the SAME principle is what makes
    "webhook AND Pub/Sub, both in M1" tractable at all.

  BETTER TOGETHER OR APART (ch. 8)
    Ingest and delivery share one event's lifecycle — that's what kills
    Hybrid. They belong together; splitting them by language is "apart"
    applied to something that wants to be "together."

  CHANGE AMPLIFICATION / COMPLEXITY DEFINITION (ch. 1)
    Hybrid means one schema change (delivery_type/delivery_config) requires
    coordinating two codebases, two CI pipelines, two deploys. That's the
    book's definition of complexity, concretely, in this decision.

  TACTICAL vs STRATEGIC PROGRAMMING (ch. 2)
    XMI wants push now. Picking Go means building unproven infrastructure
    (SQS, Pub/Sub+WIF) under that deadline — a tactical setup, "I'll harden
    it later." Picking Java means reusing infrastructure that already
    survived production — the strategic choice costs less time here, not more.

  CHESTERTON'S FENCE (ch. 15, applied both directions)
    Applied correctly: read pegleg's actual SQS listener and billing
    publisher code before proposing reuse, instead of assuming.
    Applied in reverse (the miss, corrected in 2026-07-06b): initially
    repeated the design doc's claim that cronos publishes FLOW_RUN without
    checking cronos's actual source — it doesn't own that domain at all.
    Applied forward for gangway: its fence is "own DB, own gRPC port"
    (ownership), not "must be Go" (language) — we keep the real reason,
    not the incidental detail.

  CONSISTENCY (ch. 16)
    Every service in this fleet is internally one language, with a
    generated stub in the other language for cross-language callers.
    Hybrid would be the only internally-split service — the one place a
    new engineer couldn't apply the pattern they already know from every
    other repo here.

  DIFFERENT LAYER, DIFFERENT ABSTRACTION (ch. 6)
    orinix's gRPC layer translates raw object_events rows into CloudEvents-
    shaped responses — real translation work, independent of language, but
    worth naming so this layer doesn't get built as a pass-through later.

------------------------------------------------------------------------

DECISION: JAVA. Go loses on 2 of 3 core capabilities (not all 3 — WIF is
proven in both, credit where due). Hybrid is rejected outright, not close.
