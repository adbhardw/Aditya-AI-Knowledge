4. WHY THE EVAL GATES MOVED TO JENKINS
--------------------------------------------------------------------------------

Source: docs/test-and-evaluate/eval-gates-for-agent-owners.md (new, 80 lines,
read in full) and AGENTS.md.

4.1  WHY NOT GITHUB ACTIONS

     An eval is not a unit test. It needs the whole stack up:

         postgres, langfuse, chromadb        (infra)
         agent-server on :8080               (the agent under test)
         search-server on :8081              (marketplace/example suites)
         a google-api-key credential         (the LLM judge)

     Jenkins already owns the deploy pipeline, the k8s agent pods
     (k8sAgentYaml(cpu: '4', memory: '8Gi') in the Jenkinsfile) and the
     credential store. GitHub Actions has none of that.

     The GHA workflows are kept as workflow_dispatch MANUAL FALLBACKS rather
     than deleted -- the migration stays reversible.

     Two new Jenkins stages (named in the doc; the stage bodies themselves
     were NOT read in the Jenkinsfile):
         "Validate Eval Matrix"   -> scripts/ci/check_eval_matrix.py
         "Eval Gates"             -> scripts/ci/run_eval_gates.sh
     Jenkins archives eval-report.json and eval-reports/** from Eval Gates.


4.2  COVERAGE BY DEFAULT, NOT BY OPT-IN — the real design idea

     With 18+ graphs across many owning teams, a gate teams must opt into only
     measures the teams who were already careful. New agents land uncovered
     and nobody notices.

     Three mechanisms make coverage the default:

     (a) [agent.default] in scripts/ci/eval_matrix.toml is a generic
         agent-server smoke. The CI runner INJECTS the registry graph_id for
         every touched enrolled agent. The doc is explicit:
             "no per-agent smoke entry required"
             "do not hand-edit a per-agent smoke block"
         Empty thresholds mean the gate is "agent responds + eval pipeline
         completes" -- deliberately weak, but non-zero and automatic.

     (b) check_eval_matrix.py runs as a Jenkins stage that FAILS THE PR on
         coverage violations. The gate enforces its own adoption.

     (c) AGENTS.md adds it to the new-agent checklist marked "do not skip":
             1. Register _HYPHEN_AGENTS + run uv run registry / core/compile.py
             2. Must run check_eval_matrix.py (and ensure_eval_matrix_entry.py
                if evaluation/ exists)
         So the instruction reaches both humans and the coding agents that
         read AGENTS.md.


4.3  FOLDER-SCOPED TRIGGERS

     A change under core/agents/marketplace-search/ does NOT run
     segmentation/xmi/cleanroom evals.

     eval_matrix.toml maps change categories to checks via git pathspecs.
     Categories read: prompts, tools, models, retrieval, guardrails.
     Example:

         [categories.retrieval]
         paths = ["core/agents/marketplace-search/**",
                  "compatibility/search/**",
                  "core/**/*retrieval*", "core/**/*chroma*",
                  "core/**/*embed*"]

     Two run types per category:
         eval_ci  -> scripts/eval_ci.py, JSON datasets against a live agent URL
                     with thresholds like {faithfulness = 0.49, recall_at_5 = 0.0}
         uv_eval  -> uv run eval <target>, Langfuse experiments / golden tests

     Rationale: without scoping, every PR pays for every agent's evals, CI
     time explodes, and teams route around the gate. A gate people avoid is
     worse than no gate, because it also produces false confidence.

     Nice detail -- deliberate rubric alignment for dedupe:
         "# Same rubric fields as [agent.marketplace_search] rag run so
          dedupe merges to one batch."


4.4  GRADUATED ENFORCEMENT — the mature call

     Three named, VISIBLE downgrade paths:

         advisory = true      on a uv_eval block: runs, reports
                              "ADVISORY FAIL: <target>", never blocks. Used
                              today by several agents "while their teams fix
                              harness issues."
         opt_out = true       + a REQUIRED reason. Reference stubs only.
         EVAL_REGRESSION_     POST /eval/compare regression check is advisory
         ALLOWLIST            unless the agent is listed.

     The principle:

         A gate with no legitimate downgrade path gets DISABLED outright.
         A gate with a named, visible downgrade path stays on and stays honest
         about what is degraded.

     "ADVISORY FAIL" in the log is strictly more information than a deleted
     CI job. The re-enable path is documented as: get
     `uv run eval <folder>` passing locally, then delete advisory = true.


4.5  THE FAILURE-TRIAGE TABLE (from the doc, reproduced because it is the
     most reusable artifact in the PR)

     Validate Eval Matrix fails    -> invalid default smoke / bad opt-out /
                                      bad uv_eval; advisory must be boolean
                                      and only on uv_eval
     eval_ci threshold / rubric    -> score below matrix threshold; fix agent
                                      or relax threshold DELIBERATELY
     uv run eval exit 1            -> golden threshold miss; fix agent or
       (non-advisory)                 adjust eval_config.thresholds
     ADVISORY FAIL: <target>       -> non-blocking; owning team should fix
     Agent-server / health timeout -> stack did not come up; check archived
                                      logs, ensure google-api-key exists
     :8080 graph_id missing        -> assistant not registered; confirm
                                      registry name maps from the agent dir

5. WHY POSTGRES STORAGE, BASELINES, AND DETECTORS
--------------------------------------------------------------------------------

5.1  WHY PERSISTENCE

     Eval jobs, rubrics and score baselines were IN-MEMORY -- they died with
     the process. You could score a PR but not answer "is this worse than last
     week?" A regression gate is DEFINITIONALLY a comparison against a stored
     prior, so the gate could not exist without the tables.

     Hence 001_eval_baselines.sql, 002_eval_jobs.sql, 003_eval_rubrics.sql and
     the POST /eval/compare endpoint. An in-memory fallback is retained so
     local dev and CI without Postgres still function.

5.2  WHY THE EVAL HARNESS NEEDS ITS OWN MONITORING  (MLOP-459, PR #1041)

     This is the subtle one and the best idea in the epic.

         A judge call that FAILS returns value == 0.0.
         A genuinely bad agent response ALSO scores 0.0.

     Without a detector, "the eval service is broken" and "all evals green"
     produce THE SAME DASHBOARD. The gate would report success precisely when
     it had stopped working.

     Three detectors, from the MLOP-459 ticket text:

         JudgeSaturationDetector  -- judge semaphore waits / 429s. The
                                     _judge_semaphore caps at
                                     config.max_concurrent_judge_calls = 5,
                                     so under load judging degrades silently.
         ZeroScoreSpikeDetector   -- share of value == 0.0 over a threshold.
                                     Ticket acceptance criterion: fires when
                                     >10% of a metric's scores are 0.0.
         ScoreDriftDetector       -- PSI (population stability index) against
                                     a trailing-7-day baseline.

     Each returns Anomaly(metric, severity, observed, expected, trace_ids).
     Acceptance criteria require no false positives on a healthy baseline
     sample.

     *** NOT VERIFIED: detectors.py was NOT read. Everything in 5.2 comes from
         the Jira ticket description, not the code. The thresholds, the
         semaphore cap, and the Anomaly shape are unconfirmed. ***

            should run in a worker thread. Blocks the event loop.

  MAJOR     scripts/ci/run_eval_gates.sh:110

            (docker run -d --name agentic-eval-...), so RE-RUNS FAIL.

  MAJOR     Jenkinsfile:259

Pattern worth noting: three of the seven (eval_plan, ensure_eval_matrix_entry,
run_eval_gates.sh) are defects IN THE GATE ITSELF -- false-positive failures,
broken idempotency, non-rerunnable containers. A gate that fails spuriously or
cannot be re-run is a gate that will be bypassed. These matter more than their
severity labels suggest.
