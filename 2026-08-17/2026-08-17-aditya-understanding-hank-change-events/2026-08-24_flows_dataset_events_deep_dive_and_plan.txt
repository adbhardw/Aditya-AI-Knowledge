2. THE MECHANISM THAT KILLS 2, 3 AND 5
=============================================================================
hank/db/change_events.go:270-276:

    // An empty ObjectID means the caller passed an empty struct to
    // Delete/Update, so the id lives only in the WHERE clause and the event
    // would be unusable to a consumer. Drop it loudly rather than emitting an
    // unresolvable id.
    if a.ObjectID == "" {
        hlog.LogEntryCtx(ctx).WithFields(...).Warn("change event skipped: empty ObjectID")
        return
    }

The guard is correct -- an event with no objectId is useless to a consumer whose
whole contract is "GET the resource by objectId". The problem is how many write
sites trip it.

This is a SECOND failure class, distinct from the claims() gate at
hank/db/audit.go:152 documented in
2026-08-17_method_find_silently_skipped_change_events.txt. A write can have
perfectly good auth claims and still emit nothing because of the struct it
passed to gorm.

  NODE-LEVEL FAILURE (#1) IS A HARDER PROBLEM:
    unhygienix/models/flows.go:255-261  FlowNode embeds ONLY TimeAudit. NO
                                        hdb.Audit. It is also a structural
                                        record (FlowID, NodeID, FlowVersion) --
                                        it carries no run state at all.
    There is no CleanRoomFlowNodeRun model. Node execution state is reached
    through the node's clean room question run, and pegleg discovers it by
    polling getActivityStatus rather than by reading a node-run row.

    So "emit an event when a flow node fails" has no row to hang off today.
    Options, in order of preference:
      (a) Emit at the QUESTION RUN level. A flow node that is a question node
          resolves to a CleanRoomQuestionRun; a failure there is the real event.
          Confirm CleanRoomQuestionRun embeds hdb.Audit and check its write
          sites for the same empty-struct pattern. Cheapest and truest to the
          system of record.
      (b) Emit FLOW_RUN with a failed status and a node identifier in the
          payload. XMI then reads the flow run back and sees which node failed.
          Fits the existing FLOW_RUN mapping; requires the payload to carry more
          than objectId, which conflicts with the "no from/to, read back by id"
          decision from 2026-07-30 (D1).
      (c) Introduce a node-run model. Correct long term, far too big for this
          work.
    RECOMMEND (a), with (b) as the fallback if XMI needs flow-level granularity.
    THIS NEEDS A DECISION FROM XMI ABOUT WHAT GRANULARITY THEY ACTUALLY CONSUME.

3.2 FLOW DELETED  (event #3)

    unhygienix/db/flows.go:413-427  DeleteCleanRoomFlow(ctx, db, crFlow)
        :427   err := tx.Scopes(IDScope(crFlow.ID)).Delete(&models.CleanRoomFlow{}).Error

    Note the irony: the function RECEIVES crFlow with a populated ID and then
    throws it away by passing an empty struct to Delete. Same at :404 for
    models.Flow{} inside DeleteFlow (:324).

    This is the cheapest fix in the whole document -- pass the struct:
        tx.Scopes(IDScope(crFlow.ID)).Delete(crFlow)
    gorm still applies the scope; the difference is that the audit hook can now
    read the primary key off the model. Verify against
    hank/db/audit.go getObjectDetails (:250) before assuming.

3.3 DATASET ASSIGNED TO A QUESTION  (event #4) -- the one that works

    MODEL: unhygienix/models/cleanroom.go:485-500  CleanRoomQuestionDataSet
           embeds hdb.Audit at :487. Carries CleanRoomQuestionID (:488),
           DataSetID (:489), Status (:492), CleanRoomFlowRunID (:497).

    WRITE: unhygienix/db/cleanroom_question_dataset_fields.go:68+
           AssignCleanRoomQuestionDataset opens BeginTxDB at :73, then:
             :80   scopes.Delete(&models.CleanRoomQuestionDataSet{})  <- clears
                   the previously assigned dataset for that crq+macro.
                   EMPTY STRUCT -> that un-assignment emits NOTHING.
             then  tx.Create(crDataSet) -> real ID -> CREATE EVENT FIRES.

    So an assignment emits a create event, but the implicit REPLACEMENT of the
    previous dataset is invisible. XMI sees "dataset X assigned" and never sees
    "dataset Y unassigned". For a reassignment they will end up believing both
    are attached unless they re-read the full list -- which, to be fair, the
    read-back-by-id contract makes them do anyway. Worth confirming with them.

    NAMING TRAP -- must be fixed before XMI codes against it:
      The Go type is CleanRoomQuestionDataSet, with a capital S in "Set".
      It is NOT in businessObjectTypes (hank/db/change_events.go:321-326, which
      only maps DataImportJob, CleanRoomFlow, CleanRoomFlowRun, Dataset), so it
      falls through to screamingSnake() at :368.
      screamingSnake inserts an underscore before an upper-case letter that
      follows a lower-case one, so the S in "Set" starts a new word:

          CleanRoomQuestionDataSet  ->  CLEAN_ROOM_QUESTION_DATA_SET

      That is almost certainly not what XMI expects, and it will end up in
      `type` and `subject` too
      (com.liveramp.cleanroom.clean_room_question_data_set.created).
      FIX: add an explicit entry to businessObjectTypes, e.g.
          "CleanRoomQuestionDataSet": "QUESTION_DATASET",
      This is exactly the case the comment at :353-363 anticipates.

3.4 DATASET REMOVED FROM A QUESTION  (event #5)

    Every removal path uses the empty-struct pattern:
      unhygienix/db/cleanroom_question_dataset_fields.go:65
          DeleteCleanRoomQuestionDatasetsByFlowRunID
          db.Scopes(CleanRoomFlowRunIDScopeExact(flowRunID)).Delete(&models.CleanRoomQuestionDataSet{})
      unhygienix/db/cleanroom_question_dataset_fields.go:80
          the implicit un-assign inside AssignCleanRoomQuestionDataset
      unhygienix/db/cleanroom_question.go:84
          Delete(models.CleanRoomQuestionDataSet{})
      unhygienix/db/cleanroom.go:2095-2097
          DeleteCleanRoomQuestionDatasetInTransaction
          tx.Scopes(CleanRoomQuestionIDScope(...)).Delete(&models.CleanRoomQuestionDataSet{})

    HARDER THAN 3.2, because these are BULK deletes scoped by question id or
    flow run id, not by primary key. There is no single object id to put in the
    event -- one call can remove N rows. Passing a struct does not help.
    Options:
      (a) SELECT the affected rows first, then delete, and emit one event per
          row. Correct, N+1 shaped, and needs the emission to happen in the
          service layer rather than the hook.
      (b) Emit a single event on the PARENT (the clean room question) saying
          "its dataset set changed", and let XMI re-read the question's
          datasets. Fits the read-back contract and is one event instead of N.
      (c) gorm v1 cannot give you the deleted rows from a scoped delete without
          a prior SELECT, so there is no free option.
    RECOMMEND (b) -- it matches the read-back-by-id contract already agreed with
    XMI on 2026-07-30, and it keeps the emission in the hook.
    NEEDS AN XMI DECISION: is a "question datasets changed" event enough, or do
    they need per-dataset removal events?
