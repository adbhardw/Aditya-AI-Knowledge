STEP 0 — DISCOVERY (paste this first, read the answer, then continue)
================================================================================

Using the Loki datasource grafanacloud-habu-logs, run this query over the last
15 minutes and show me 5 raw log lines verbatim:

{service_name="external-api-server", cluster=~"eks-admin-prod"} |= "Token request successful"

Then tell me exactly three things:
1. Are these lines JSON-encoded, or plain text with a logging prefix?
2. What is the exact text between the log level and "Token request successful"?
3. List every label available on this stream (not fields — labels).

--------------------------------------------------------------------------------
Based on the answer, pick ONE parser line and use it in every query below.
Everywhere you see  <<PARSER>>  substitute your chosen line.

  If the lines are PLAIN TEXT (most likely, Spring Boot default):
    | pattern `<_>clientID=<clientID>, userId=<userId>, organizationID=<organizationID>`

  If pattern fails to extract, fall back to regexp:
    | regexp `clientID=(?P<clientID>[^,]+), userId=(?P<userId>[^,]+), organizationID=(?P<organizationID>\S+)`

  If the lines are JSON:
    | json | line=~".*Token request successful.*" | pattern `<_>clientID=<clientID>, userId=<userId>, organizationID=<organizationID>`

Note on cost: organizationID and clientID are parsed FIELDS here, not stream
labels. Aggregating by them does not create new Loki streams and does not
increase cardinality on the index. Never promote them to labels.

PREREQUISITE
------------
The API gateway must emit one structured access log per request containing at
minimum:
    organizationID  clientID  route  method  status
    latencyMs       rateLimited  reason  limit  remaining  requestId

Two specific code changes make Part B possible:

  1. The gateway's rate-limit rejection currently logs a plain string with
     "org=" and no status code. Change it to the same key=value shape the
     token-success line uses, so organizationID parses out identically:
       Rate limit exceeded organizationID=<id>, clientID=<id>, route=<path>,
       method=<verb>, status=429, limitPerSec=<n>, retryAfterSec=<n>

  2. Auth0Service logs only on SUCCESS, after the Auth0 round trip. Add
     equivalent logging on the failure paths (product-not-enabled rejection and
     Auth0 errors), otherwise a client flooding with a bad secret produces zero
     dashboard signal while still consuming resources. Suggested shape:
       Token request failed organizationID=<id>, clientID=<id>,
       reason=<PRODUCT_DISABLED|AUTH0_REJECTED|INVALID_CREDENTIALS>

Once those land, the parser line for gateway logs becomes:
    | logfmt        (if you adopt strict key=value with no prose prefix)
  or
    | pattern `<_>organizationID=<organizationID>, clientID=<clientID>, route=<route>, method=<method>, status=<status><_>`

================================================================================
PANEL RULES — WHY THESE QUERIES LOOK LIKE THIS
================================================================================
Paste this section to the Grafana assistant if it proposes a different shape.

1. Use count_over_time([window]), never rate(...[$__auto]) * 3600.
   rate() over a short auto-selected window measures a burst and then
   extrapolates it across a whole hour. On bursty traffic it inflates wildly:
       10 events in a 2-minute burst, then 58 minutes of silence
         rate([2m]) * 3600  = (10/120) x 3600 = 300   <- fiction
         count_over_time([1h]) = 10                   <- truth
   This is exactly the defect that made an existing panel on this dashboard read
   "780 req/m" when the real figure was ~73 per hour.

2. Min interval must equal the range vector.
   [1h] only sets how far back each point looks — it does not control how many
   points are plotted. Without Min interval = 1h, Grafana picks its own step
   (~15-20 min on a 24h range) and you get overlapping one-hour windows sampled
   every 20 minutes, landing on :15 and :45 marks instead of clean hourly bars.

3. Unit must match the expression's real dimension.
   A count per hour under a "req/m" unit is wrong by 60x and nothing in the UI
   warns you. For bucketed counts use short or none. Never reqpm on a
   count_over_time panel. For ratios use none or percentunit — never a rate unit.

4. Time series + Draw style Bars, not the Bar chart panel.
   The Bar chart panel is for categorical data. Time-bucketed counts belong on a
   Time series panel with the bars draw style.

5. Line filter before parser.
   Always put |= "Token request successful" before the pattern/regexp parser.
   Filtering first is dramatically cheaper than parsing every line.

6. Keep organizationID and clientID as parsed fields, never as stream labels.
   Loki creates one stream per unique label combination. Promoting a tenant id
   to a label multiplies streams by the tenant count. Parsed fields cost nothing
   on the index.

7. Titles must state what the panel actually measures.
   "Orgs above threshold" with no threshold configured is how a dashboard loses
   credibility. If there is no threshold, do not put one in the title.
