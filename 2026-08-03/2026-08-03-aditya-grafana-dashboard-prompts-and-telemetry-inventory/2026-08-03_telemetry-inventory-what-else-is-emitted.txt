TELEMETRY INVENTORY — WHAT ELSE IS EMITTED BESIDES "Token request successful"
Searched: external-api-server, forebitt, hank, moonraker, api-gateway (chart),
          dyogram deployment charts
Date: 2026-08-03

SHORT ANSWER
------------
Yes — considerably more, in two categories, and the second one changes the plan.

  1. LOGS: ~25 additional log statements carry organizationID, out of 390 total
     log statements in external-api-server. BUT they use four mutually
     incompatible formats, and only ONE of them is the key=value shape that
     Datadog auto-parses into a facet.

  2. METRICS: every service — including the api-gateway — already exposes
     Prometheus metrics via a ServiceMonitor. This was missed in the 2026-08-02
     investigation, which treated logs as the only source. Roughly half of the
     "blocked" panels in the dashboard prompt file are buildable TODAY from
     Prometheus, with no code change at all.

The architectural point that follows:
     METRICS answer  "how much, how fast, how broken"
     LOGS    answer  "which tenant"
     NEITHER alone answers "which tenant is being throttled" — that specific
     question still needs the gateway to log org + status together.

2. LOGS — WHAT ELSE CARRIES organizationID
================================================================================

external-api-server has 390 log statements. Roughly 25 carry an org, client or
user identifier. The complete list of org-carrying lines:

  service/auth0/Auth0Service.java:75            Token request successful     <- the one you use
  service/credential/CredentialSourceService.java:30,69,111
  service/credential/OrganizationCredentialService.java:35,64
  service/dataconnection/DataSourceService.java:36,76
  service/dataconnection/IdentifierService.java:28
  service/user/UserService.java:22
  service/cleanroom/CleanRoomService.java:35,68,237
  service/cleanroom/CleanRoomQuestionService.java:710,789,850
  service/cleanroom/CleanRoomQuestionRunService.java:494
  service/cleanroom/CleanroomQuestionRunScheduleService.java:52,123,148,166,179,242,258,269
  service/intelligence/IntelligenceService.java:50,121                       <- see below

THE PROBLEM: FOUR INCOMPATIBLE FORMATS

  Occurrences across external-api-server/src/main/java:

      organizationID={}          1     <- Auth0Service only
      organizationID {}         13     <- space separated
      organizationID: {}         9     <- colon separated
      orgId={}                   2     <- different key name entirely
      caller={} owner={} cr={}   2     <- IntelligenceService

  Consequence for Datadog: only the key=value form auto-parses into the
  @organizationID facet. The 22 lines using "organizationID <value>" or
  "organizationID: <value>" produce NO facet and cannot be grouped by org
  without a custom Grok parser in the log pipeline.

  Consequence for Loki: one regexp cannot cover all four. Either normalise the
  log format in code (preferred) or write a parser with alternation:

      | regexp `organizationID[=: ]\s*(?P<organizationID>[0-9a-f-]{8,})`

  That alternation regexp does work for the three organizationID variants but
  still misses orgId= and the caller=/owner= pair.

HIGH-VALUE LINES NOBODY IS DASHBOARDING
---------------------------------------
Two of these are more operationally interesting than request volume:

  IntelligenceService.java:50   log.warn("Org mismatch on getCleanRoomIntelligence: caller={}, owner={}, cr={}")
  IntelligenceService.java:121  log.warn("Org mismatch in authz check: caller={}, owner={}, cr={}")

  These fire when one organization attempts to access another organization's
  clean room. That is a cross-tenant authorization failure — a security signal,
  not a capacity signal. It is already in key=value form, so it is aggregatable
  today with no code change. A panel counting these by caller is arguably more
  valuable than anything in the ten-dashboard list.

  Suggested LogQL:
      sum by (caller) (count_over_time(
        {service_name="external-api-server", cluster=~"$cluster"}
        |= "Org mismatch"
        | pattern `<_>caller=<caller>, owner=<owner>, cr=<cr>` [1h]))

Also present, in the auth filters (http/filters/):
      "Missing required internal headers for path: {}"
      "Missing or invalid Authorization header for internal path: {}"
      "Invalid base64 in {} claim"
  These are authentication failures. None carry an organizationID (by definition
  — the request failed before the org was resolved), so they can be counted in
  total but not attributed to a tenant.

FOREBITT
--------
  Searched forebitt for Go log statements containing organization / orgid /
  tenant / clientid: NO MATCHES. forebitt does not appear to emit tenant-
  attributable log lines. It does ship a ServiceMonitor, so its HTTP metrics are
  available.

3. RESOLVED — PRODUCTION LOGS ARE JSON
================================================================================

Confirmed 2026-08-03 from live Grafana output. LOGBACK_APPENDER is set to "json"
in the deployment (from a source outside this repository — it appears in no
dyogram chart, values file or template).

Actual production envelope (identifiers replaced with synthetic values):

  {"@timestamp":"2026-08-03T08:43:46.141Z",
   "@version":"1",
   "message":"Token request successful for clientID=AbCdEfGhIjKlMnOpQrStUvWxYz012345, userId=11111111-2222-3333-4444-555555555555, organizationID=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
   "logger_name":"com.habu.api.external.service.auth0.Auth0Service",
   "thread_name":"qtp1216198248-16742",
   "level":"INFO",
   "level_value":20000,
   "requestId":"0f0f0f0f-1e1e-2d2d-3c3c-4b4b4b4b4b4b"}

WHAT THIS CHANGES:

  1. No | decolorize needed. The earlier concern about ANSI colour codes does
     not apply.

  2. requestId is a TOP-LEVEL FIELD, not buried in the message. Every log line
     produced while handling one HTTP request carries the same value, so you can
     correlate a tenant's request across every class it touched. This is the same
     correlation key identified independently in the hank platform-event design
     work — it is genuinely the load-bearing identifier in this estate.

  3. logger_name is a top-level field, so panels can filter by CLASS rather than
     by message substring. More precise and cheaper:
         | json | logger_name="com.habu.api.external.service.auth0.Auth0Service"
     instead of
         |= "Token request successful"
     (keep the line filter too — it prunes before JSON decoding.)

  4. level and level_value are top-level fields. An error/warning-rate-by-class
     panel needs NO message parsing at all and costs nothing to add.

  5. THE CATCH: clientID, userId and organizationID are NOT top-level fields.
     They remain embedded in the "message" string, so extraction is two-stage:

         | json
         | logger_name="com.habu.api.external.service.auth0.Auth0Service"
         | line_format "{{.message}}"
         | pattern `<_>clientID=<clientID>, userId=<userId>, organizationID=<organizationID>`

     Cheaper single-stage alternative, exploiting fixed-width identifiers —
     works on the raw JSON line with no decode:

         | regexp `organizationID=(?P<organizationID>[0-9a-f-]{36})`
         | regexp `clientID=(?P<clientID>[A-Za-z0-9]{32})`

  6. The four-incompatible-formats problem in section 2 is UNAFFECTED. The JSON
     envelope wraps the message; it does not restructure what is inside it. The
     22 log lines using "organizationID <value>" and "organizationID: <value>"
     are still not key=value, and still need either a code change or a bespoke
     regexp. Datadog's @organizationID facet works on the token line because
     Datadog auto-extracts key=value pairs from the message attribute — which is
     exactly why the other 22 lines produce no facet.

THE ONE CHANGE THAT MATTERS MOST
--------------------------------
Everything still-blocked reduces to a single missing join: no record contains
both an organization identifier and an HTTP status. Metrics have status without
org; logs have org without status.

Fix it in one place — the gateway's rate-limit rejection path — using the
key=value form so both Datadog faceting and Loki pattern parsing work:

      Rate limit exceeded organizationID=<id>, clientID=<id>, route=<path>,
      method=<verb>, status=429, limitPerSec=<n>, retryAfterSec=<n>

Second priority: normalise the 22 existing "organizationID <value>" and
"organizationID: <value>" log lines in external-api-server to
"organizationID=<value>". That is a mechanical change and it makes two dozen
existing business-operation logs aggregatable per tenant for free.
